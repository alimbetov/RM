## 1. Architecture and non-goals
Reuse authorized L0–L3 reads, DQR quality, existing IAM and file infrastructure. Report renderer consumes typed results, never recomputes business metrics. Separate report identity/metadata, optional immutable large tabular snapshot payload, and Excel/PDF artifacts. No duplicate warehouse, separate database per tenant, or mandatory persistence of every report row. Small reports may persist only immutable artifact plus evidence manifest if reproducibility requirements are met. Existing L0–L3 keys, generation lifecycle and source identities are unchanged.

## 2. Optional long-retention archive candidate (not delivery staging)
Report metadata and jobs: ordinary PostgreSQL tables, tenant-leading indexes. Large new snapshot-row table: design compatible with monthly RANGE(snapshot_month) and optional HASH(tenant_id) subpartitions; start by benchmarking unpartitioned, RANGE only and RANGE+HASH 4/8/16. Choose the simplest passing configuration before first production migration. snapshot_month is immutable first day of UTC creation month, NOT reporting business period, so a multi-year report is located in one partition and expiry does not depend on historical metric dates. Business periods remain separate calendar-versioned half-open bounds. Query by tenant, snapshot_month, snapshot_id; never derive partition routing from requested period. A hash bucket is not a security boundary. No LIST per tenant by default. Large shared partitions require per-tenant quotas and fair scheduling, not claims of physical isolation.

## 3. Optional archive logical model (not executable migration; conceptual aliases only)
report_request: PK(tenant_id,request_id); UNIQUE(tenant_id,idempotency_key); canonical request digest, actor, report type, template/method/presentation version, normalized filters, calendar version, period bounds, status. Same idempotency key with different digest is conflict.
report_snapshot: PK(tenant_id,snapshot_id); UNIQUE(tenant_id,snapshot_id,snapshot_month); FK(tenant_id,request_id); snapshot_month DATE NOT NULL; creation timestamp UTC; source revision, as_of, per-window generation/proof/quality evidence, manifest digest, row count. Enforce month equals UTC creation month by check and immutability. One request may have multiple explicitly versioned snapshots only if policy permits; retries reuse reserved identity. New revision creates new immutable snapshot.
report_snapshot_row (optional): PK(tenant_id,snapshot_month,snapshot_id,row_no); FK(tenant_id,snapshot_id,snapshot_month) -> report_snapshot; row_no positive; typed payload and schema version; RANGE(snapshot_month), optionally subpartition HASH(tenant_id). All unique constraints include every partition key. Parent metadata anchors cross-month identity; no global uniqueness claim for row table alone. Store decimal values losslessly, explicit NULL and quality, dimension identifiers and units/currency. No PII unless report contract expressly authorizes it.
report_artifact: PK(tenant_id,artifact_id); FK(tenant_id,snapshot_id); UNIQUE(tenant_id,snapshot_id,format,renderer_version); object key, digest, size, media type, status, created/expiry; immutable READY object. Metadata is authoritative; object key is not authorization.
Indexes: report_request(tenant_id,created_at DESC,request_id); report_snapshot(tenant_id,request_id); row PK supports scoped ordered streaming; artifact unique supports lookup. Add secondary period/type indexes only after query evidence. Exact DDL, status enums and retention values require approval; names are logical and must be reconciled with existing report TЗ.

## 4. Source and mathematical contract
All report metrics include metric/method version, grain, dimensions, currency/unit, calendar version, actual_as_of, source revision, route, quality and proof where applicable. Use existing bounded authorized read windows; if report spans multiple reads, require one coherent snapshot or verify immutable pinned evidence and reject mixed revisions where coherence required. Never silently combine current L0 and historical L3 from different snapshots. Current pilot BOOKED_ORDERS PARTIAL/MISSING is not COMPLETE. A qualified zero requires DQR proof. Distinct orders across categories or periods use qualified union membership, not sum of counts; ratio-of-sums, weighted averages and currency conversion use existing approved methods. Presentation formats do not change stored precision. Late facts produce new revision/snapshot; old report stays reproducible and labelled superseded, never overwritten. No historical-as-of claim from current visibility alone.

## 5. Security and publication
VerifiedActor + current tenant RBAC and report-specific underlying metric/PII permissions for request, execution and download; dedicated least-privilege service identity for background execution, not fabricated human principal. Tenant included in all keys, joins, job payloads, caches, object paths and audit. Revalidate requester authorization before publish and download; revoked membership fails closed. Do not treat tenant prefix or partition pruning as access control. Deny direct child-table access to application roles; consider RLS only with real role, pool reset, owner/bypass and partition direct-access qualification. Object keys server-generated, private objects, short-lived authorized download or authenticated streaming; signed URL revocation window explicit. No public bucket. Spreadsheet formula injection protection for untrusted text. Encryption and lifecycle follow existing platform standards.

Publication: reserve request and snapshot identity transactionally; write bounded snapshot; verify row count, ordered canonical digest and evidence; render/upload to immutable temporary/staged key; verify object digest; commit READY metadata with fencing; cleanup orphan objects asynchronously using existing infrastructure. PostgreSQL and object store are not one ACID transaction. Crash/retry must not publish incomplete artifact, overwrite prior READY, or duplicate logical publication. Explicit state/transition contract in implementation design.

## 6. Optional archive lifecycle and operation (not daily staging)
Retention separated for canonical source, projections, snapshot rows, artifact and audit metadata. No automatic deletion until tenant policy, legal hold and references checked. Month partition detach/drop only when ALL tenants' rows in it eligible and no held data; otherwise scoped row deletion or keep partition. Precreate next months, alert on missing partition, fail closed; no silent unbounded default partition. Restores and replays preserve identity and digest; qualify backup/restore and tenant-specific export/delete. Monitor per-tenant bytes, row count, report concurrency and latency, queue age, partition count, skew, autovacuum, index size, WAL, lock duration, pool usage. Prefer streaming bounded batches to memory-heavy rendering.

## 7. Optional archive capacity and qualification
Illustrative rows = tenants * reports per tenant per month * rows per report * retained months; not all analytical cells need copying. For 1000 tenants, 10 reports/month, 1000 rows/report, 24 months: 240M rows if every report persists rows; RANGE 24 leaves, RANGE+8 HASH 192 leaves. Actual size = measured table + indexes + TOAST + artifacts, plus separately measured WAL/backup. Hash balance depends on tenant size; large tenant remains in one bucket per month.
Compare same fixture, same workload and PostgreSQL version: 10/100/1000 tenants, skewed hot tenant, 1/12/24 months, concurrent generation/download and OLTP; measure p50/p95/p99 per operation, planning/execution, buffers, partition pruning, temp spills, writes/WAL, vacuum, storage, queue age. Reuse Q2-FINAL P5 matched OFF/ON business thresholds p95<=10%, p99<=20%, zero deadlocks/pool timeouts; report-specific SLA and resource budgets require approval. Do not infer speedup from partition count. Prefer unpartitioned or RANGE-only if targets met. Admission requires exact parity against qualified analytical source; zero cross-tenant reads/writes/downloads, duplicate publish, missing rows, mismatched hashes, unsafe deletion; crash recovery across pods; boundary month/DST, late data, restore, revocation, direct partition access and multi-year report tests. Exact-SHA required for implementation. Design only; no runtime evidence claimed.

### 9.2 SQL model and constraints
Proposed reporting schema; reuse existing registry/job/file owner tables if equivalent. Minimal persistent roles:
- int_report_instance PK(tenant_id,instance_id), UNIQUE(tenant_id,idempotency_key), immutable request/actual scope digest and passport, current lifecycle, job reference; mutable visibility version/ACL separate from content. Tenant/workspace FK and all cross-entity FK tenant-scoped.
- int_report_visibility keyed by tenant/instance and approved audience grant identity; grant version/audit, default private, revocation independently mutable.
- Durable dataset attempt metadata (embed in existing job/instance metadata if it supports all invariants; otherwise minimal int_report_dataset_attempt): PK(tenant_id,dataset_id), UNIQUE(tenant_id,dataset_id,staging_date), immutable UTC allocated date and source manifest, monotonic attempt token, state, row count/digest, lifecycle/recovery deadlines. Instance-to-dataset consumer links include tenant and dataset; reuse only identical scope/evidence with separate access checks. Lease/pin records and per-consumer terminal timestamps must be durable (reuse job metadata if sufficient); never infer all consumers from current staging rows. No FK from durable history to disposable staging rows.
- int_report_dataset: daily RANGE(staging_date), PK(staging_date,tenant_id,dataset_id,row_key), FK(tenant_id,dataset_id,staging_date) to durable attempt identity; row_key deterministic total order (e.g. fixed-width canonical ordinal), typed decimal NUMERIC, explicit quality, nullable value per admitted metric contract, unit/currency, dimension and period references. No DEFAULT, initially no HASH. All row access binds tenant/date/dataset. PK already supports ordered scan with equality on date/tenant/dataset; add tenant-first local secondary index only if EXPLAIN proves benefit. All constraints/index grants verified on each child. Separate canonical digest format version; do not hash unstable Java toString or rounded Excel cells.
- Optional artifact mapping only if existing File Service binding cannot express tenant/instance/format/version identity. Unique logical format publication, immutable file digest, no raw public URL. No direct child privileges for app; parent ACL not a substitute for tenant predicates.

Candidate daily DDL (illustration only):
```sql
CREATE TABLE reporting.int_report_dataset (
 staging_date date NOT NULL, tenant_id uuid NOT NULL,
 dataset_id uuid NOT NULL, row_key bigint NOT NULL CHECK(row_key>0),
 metric_code text NOT NULL, metric_value numeric,
 quality_code text NOT NULL,
 PRIMARY KEY(staging_date,tenant_id,dataset_id,row_key),
 FOREIGN KEY(tenant_id,dataset_id,staging_date)
 REFERENCES reporting.int_report_dataset_attempt(tenant_id,dataset_id,staging_date)
) PARTITION BY RANGE(staging_date);
```
Not complete executable migration: remaining typed schema, quality enum/checks, grants, immutability guards and job integration required. If attempt metadata reused rather than separate table, FK target must preserve equivalent unique identity. No archive by default.

### 9.3 Transaction and lock graph
T0 request: short RC, IAM actor/workspace + owner scope, then request identity/ACL; persist digest and intent atomically. T1 claim: queue row only, SKIP LOCKED, commit before IAM or partition fence. T2 allocate: shared transaction-scoped partition fence then attempt row; require OPEN date from DB UTC clock; persist allocated date; commit. T3 analytical extraction: existing own transaction boundary (do NOT call within an active report transaction), authorized consistent bounded RR; close it before rendering. For bounded payload retain in memory within approved budget or design qualified streaming extraction under one source snapshot with measured resource budget; no implicit cross-transaction consistent read or unsafe revision-only check. T4 append: partition shared fence then attempt row, fresh DB time and token, insert bounded ordered batch; duplicate row allowed only identical canonical content; reject stale/retired; commit. T5 READY: same fence order, validate complete manifest/count/digest, immutable READY transition atomically. T6 render: acquire durable pin in short fenced transaction, page reads each verify live pin/token under shared fence, heartbeat/renew bounded; no DB transaction during file conversion/upload. T7 file staging/scan/attach uses existing admitted File Service owner locks and immutable attempt-specific file identity; no partition lock around network IO. T8 publish: IAM/owner scope -> report instance/visibility -> approved file lock protocol, fresh lease/token and verified file refs, atomic publication of durable metadata; no partition fence in this transaction. Consumer terminal acknowledgement in separate partition-fenced T9 transaction after durable publication; until ACK cleanup conservatively blocked. Recovery reconciles publication evidence idempotently, never marks successful publication based on upload alone. T10 cleanup: exclusive partition fence -> durable attempts/consumers/pins in canonical order -> verified child DDL, atomic retired marker and DROP, bounded lock timeout; no IAM/file/network operations under fence. Report publication and cleanup shared data dependency mediated by durable consumer state; no report lock acquired under lifecycle fence if it participates in reverse order. Full cross-component lock DAG and revoke races require qualification before implementation.

### 9.4 Multi-pod lifecycle
Use proposed transaction advisory fence with reserved application namespace and stable integer day key (days since epoch), same key for create/allocate/pin/write/seal/cleanup; shared for access, exclusive for create/drop. All code paths must obey it; lock is coordination, not authorization. Verify namespace collisions and owner grants. DB-derived UTC date, deterministic child name from trusted date only. Narrow privileged maintenance routine verifies actual parent OID, bounds, indexes, grants, lifecycle/tombstone; no IF NOT EXISTS-only success. Fixed bounded lookahead current + 2 days; existing coordination invokes maintenance on startup/recovery and daily. No unbounded catch-up creation; never recreate retired dates. OPEN to SEALED derived under fence at UTC midnight, existing attempt pins may continue. RETIRED tombstone durable; missing unexpected child fails closed, not silent recreate of active data. Distinguish retry same live attempt vs new attempt after retirement; no stale token write into new dataset. On pod crash lease expires, takeover increments token; old writer blocked even if it resumes. An expired lease is not alone sufficient for drop: no active shared transaction, no unresolved consumer/file/evidence or hold. Cleanup uses exclusive fence and rechecks all metadata and orphan rows, no active pin, all consumer dispositions and >=24h since last successful publish (failed abandonment grace separately approved), then drop verified child and persist retirement in same DB transaction. Crash before commit rolls back both. Lock contention defers maintenance, no unsafe force-drop. Monitor oldest sealed blocked day, missing partition, capacity and WAL; backpressure on disk budget. Report-specific SLA and exact limits pending approval.
