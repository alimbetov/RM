## 3. Contract B — immutable durable outcome / acknowledgement

Decision proposed: one narrow logged PostgreSQL table crm.int_intraday_result, one request/outcome per existing INTRADAY job. Not a second scheduler, report dataset, warehouse, outbox, or File Service artifact. The durable internal consumer INTRADAY_SNAPSHOT_STORE_V1 acknowledges by atomically committing the exact outcome with job COMPLETED. This is storage acknowledgement ONLY; no report/Radar delivery acknowledged. A future approved report consumer uses its own S4/S5 lifecycle with fresh authorization, never assumes job completed means delivered. If the owner requires an external consumer acknowledgement rather than this bounded storage consumer, keep R1.3 blocked until that consumer is admitted. Do not mark COMPLETED on merely computing an in-memory value.

Proposed v1.2 physical shape (supersedes original JSONB request/result columns; review deployed DATABASECHANGELOG first, no changeset ID assigned). For single fixed pilot metric use typed relational columns, no duplicate JSON passport. Existing job row remains authoritative for tenant, job, nominal slot, businessDay, calendar and zone. Result row owns scope/actor, day bounds and actual outcome.
```sql
CREATE TABLE crm.int_intraday_result (
  tenant_id uuid NOT NULL,
  job_id uuid NOT NULL,
  schema_version smallint NOT NULL CHECK (schema_version=1),
  consumer_code varchar(48) NOT NULL
    CHECK (consumer_code='INTRADAY_SNAPSHOT_STORE_V1'),
  service_account_id uuid NOT NULL,
  scope_version bigint NOT NULL CHECK (scope_version>0),
  scope_digest char(64) NOT NULL CHECK (scope_digest ~ '^[0-9a-f]{64}$'),
  metric_code varchar(32) NOT NULL CHECK (metric_code='BOOKED_ORDERS'),
  method_version integer NOT NULL CHECK (method_version=1),
  day_start timestamptz NOT NULL,
  day_end timestamptz NOT NULL CHECK (day_start<day_end),
  actual_as_of timestamptz,
  read_observed_at timestamptz,
  source_revision bigint CHECK (source_revision>=0),
  metric_value bigint CHECK (metric_value>0),
  quality varchar(16) CHECK (quality IN ('PARTIAL','MISSING')),
  quality_reason varchar(64),
  result_digest char(64) CHECK (result_digest ~ '^[0-9a-f]{64}$'),
  acknowledged_at timestamptz,
  PRIMARY KEY (tenant_id,job_id),
  FOREIGN KEY (tenant_id,job_id)
    REFERENCES crm.int_analytics_job_run(tenant_id,job_id),
  CHECK ((acknowledged_at IS NULL AND actual_as_of IS NULL
      AND read_observed_at IS NULL AND source_revision IS NULL
      AND metric_value IS NULL AND quality IS NULL
      AND quality_reason IS NULL AND result_digest IS NULL)
    OR (acknowledged_at IS NOT NULL AND actual_as_of IS NOT NULL
      AND read_observed_at IS NOT NULL AND source_revision IS NOT NULL
      AND quality IS NOT NULL AND quality_reason IS NOT NULL
      AND result_digest IS NOT NULL
      AND day_start<=actual_as_of AND actual_as_of<day_end
      AND actual_as_of<=read_observed_at
      AND read_observed_at<=acknowledged_at
      AND ((quality='PARTIAL' AND metric_value IS NOT NULL
          AND quality_reason='PERIOD_NOT_CLOSED')
        OR (quality='MISSING' AND metric_value IS NULL
          AND quality_reason='NO_QUALIFIED_OBSERVATION'))))
);
REVOKE ALL ON crm.int_intraday_result FROM PUBLIC;
```
Count from existing BigDecimal L0 result must convert with longValueExact, reject fractional/overflow/nonpositive instead of truncating; do not change existing metric SQL. Unit COUNT, route L0, null currency/filters/generation/proof implied by schema v1; canonical derived payload includes explicit nulls and versioned typed values. No JSONB duplication or generic metric EAV. Expansion requires reviewed typed payload version and units; do not add dynamic columns or second metric engine now.

Same migration must enforce exact parent type, calendar/day/slot/bounds, immutable request, exactly one null-to-ack transition, immutable acknowledged row, no DELETE/TRUNCATE by runtime; deferred constraint triggers on BOTH parent and result enforce completed iff acknowledged with matching actual_as_of/source_revision. No state mutation of NIGHT from these triggers. Recheck final state by tenant/job, not trigger OLD/NEW alone. No orphan request or completed INTRADAY without result. Legacy unadmitted fixture rows with no result may remain PENDING/non-executable; explicitly inventory any completed legacy rows and fail migration if inconsistent (no fabricated payload). New enqueue parent+request atomically. Guard transition using persisted lease owner/token/slot under job lock and approved authority, not a freely caller-supplied identity. Scope drift cannot mutate stored request. Digest is integrity/identity check not proof of authenticity: build canonical envelope from joined authoritative fields, fixed key order, UTF-8, explicit null, UTC micros, UUID lowercase, count as decimal string, SHA-256 lowercase; recompute on read. If DB cannot verify digest independently without new extension, no assertion of DB digest enforcement; consistency constrained in DB and digest verified by trusted application. No arbitrary payload accepted. Runtime role cannot insert/update/delete/truncate result directly; narrow guarded routines proposed for registration and acknowledgement, with fixed search_path and revoke PUBLIC EXECUTE, reviewed role grants; see §8.

Canonical request contains tenant/job/slot/calendar/zone/day, day bounds, service account, scope version/digest, consumer, method/metric and explicit no filters. Scope digest excludes job/slot; exact equality on registration conflict ignoring only losing randomly allocated job ID. Result adds event cutoff actualAsOf, readObservedAt, sourceRevision, count/null, quality/reason, acknowledgement, result digest (digest excludes itself). Canonical size <=16 KiB enforced on serialization; row shape bounded by typed columns. Persist acknowledgement timestamp sampled once by DB in guarded write, not claimed commit time. No access tokens, raw owner rows or PII. Latest authorized read selects current compatible day/calendar/scope and greatest cutoff, tie-break slot/job; never sum outcomes or return old day as current. No public endpoint. Pilot stop budget mandatory (tenant count, duration, max admitted slots/rows and storage), proposed no automatic deletion; report staging partition lifecycle separate. Seven nominal slots per pinned compatible local day, not seven per rolling 24h.

Lost commit response recovered by immutable job+result. Release slot only with durable terminal transition. Explicit skip/blocked reason stored; do not pretend read succeeded.

## 8. Re-audit v1.2 — normative proposed clarifications (supersede conflicting earlier wording)
A1. Durable identity classification: actual iam_user_account currently lacks human/service discriminator. Proposed additive principal_kind HUMAN/SERVICE, existing rows default HUMAN only after explicit inventory of any existing workload accounts. SERVICE provisioned only by controlled IAM owner operation with verified external_subject and fixed client mapping; ordinary human account provisioning cannot set SERVICE, no automatic startup creation, no silent SERVICE->HUMAN conversion. Existing user resolver rejects SERVICE; ordinary HTTP admission rejects service audience/client AND durably classified SERVICE subject even if ordinary-audience-only token was issued; verify all user entrypoints, not just one decoder. Service resolver requires SERVICE + exact client/subject/issuer/service-only audience, active account and expiry. Name/qualify decoders and explicit HTTP wiring; no fake VerifiedActor or token logs. Narrow typed service admission uses existing RBAC actor/workspace locks and fresh SQL for classification/enforced config/active membership/permission allowlist; no general public UUID-based authorization shortcut. Existing owner/member/role writers already lock actor then workspace; retain protocol. Actual IAM schema change/role provisioning/issuer approval still open.
B1. Threat model: existing shared application login + composite FK does not provide per-tenant SQL isolation. Trust authenticated internal Java admission; DB enforces durable consistency, denies direct writes to result and arbitrary terminal transition through runtime grants. Guarded registration/ack routines SECURITY DEFINER only if necessary, nonlogin owner, schema-qualified SQL and fixed search_path, no caller-defined SQL/role, no PUBLIC execute; verify current job and exact attempt, parent/scope/identity and allowed transitions. A function supplied with caller UUID/lease cannot cryptographically verify service JWT by itself; do not claim it prevents a compromised trusted application from impersonating another admitted tenant or fabricating a mathematically valid count. DB-enforced hostile-session isolation would require separate authenticated tenant/workload credential boundary or qualified RLS; not included/approved here. Positive actual grants for scheduler and NIGHT compatibility must be reviewed; if shared existing runtime can bypass protected writes, runtime HOLD, do not claim least privilege. Negative tests for untrusted login, wrong tenant/job combination, forged attempt, direct ack, DELETE/TRUNCATE. Distinguish application cross-tenant denial from DB structural integrity and actual role privileges.
B2. Lock DAG: never wait on existing job row while holding workspace/actor locks in planner. Plan discovery may read eligibility without locks; registration serialized under workspace fence only for new immutable parent/request and fresh read of existing winner, no updates to existing jobs under workspace lock; on unique collision/lock timeout rollback and retry in fresh transaction. Reconciliation of old/expired rows separate job-first transaction; same job->actor->workspace->organization order as execution, organization NOWAIT/bounded. Prove planner vs activation, coalescer vs claim, RBAC revoke vs read, FK/index waits using actual pg_blocking_pids and timeouts. No source/business writer acquires job lock. If any lock inversion remains, stop and repair before enabling.
B3. Temporal boundary: pin UTC [dayStart,dayEnd) and calendar/scope for each admitted business day. Under serialized tenant registration reject candidate when calendar/scope drift within prior admitted day or new day window overlaps an earlier incompatible pinned window; do not compute retroactive day or invent extra slots. Resume only at next non-overlapping eligible day or explicit owner reconciliation. Same nominal local day under incompatible policy blocked; same instant dedup; skipped slots retained for diagnostics. Seven per stable local day, not fixed rolling exposure. Final write uses one DB clock sample plus fencing trigger; commit may physically finish later. Define admission/ack linearization at guarded transition, not guaranteed instant of transaction commit. Current-day latest reads always re-evaluate current local day, never present a prior-day outcome as current, even if commit crossed midnight. Missed next slot coalesces only unacknowledged work; already committed outcome immutable. No hard SLA or proof of physical exactly-once.
C1. Statistical evidence: actualAsOf is event cutoff (transaction_timestamp), readObservedAt is separate sampled clock after RR snapshot acquisition, ack sampled at final write, none is historical commit timestamp or MVCC snapshot serialization. Source revision is frozen baseline + count of visible append-only tenant revision events, not max sequence, event count or unique snapshot ID. Unrelated owner events can change revision without changing metric. Never deduplicate by revision alone; compare full scope and observation identity. Existing source view groups PLACED per tenant/order/type HAVING count(*)=1 over ALL visible events before filtering cutoff and joins lines; the independent oracle must reproduce eligibility over all visible events, not filter before HAVING, including ambiguous duplicate outside cutoff. Existing status-event DDL PK tenant/event ID does not by itself enforce uniqueness per order/type. No new source rule or owner mutation in R1.3. MISSING null even for no eligible rows; known ambiguous source inconsistency blocks or explicit diagnostic abstention, not a qualified zero. Exact count does not imply completeness.
C2. Comparative and predictive methods remain HOLD. Define future point-in-time evaluation unit as one tenant × day class × matched elapsed cutoff × stable scope/method. No pooling cumulative slots as independent observations, no ratio from unknown denominator, no treating missing schedule as random, no naive extrapolation by hours elapsed. No approved sample size, MAD multiplier, Poisson assumptions, ML or new operators in R1.3. Existing B5 closed READY gates intact.
