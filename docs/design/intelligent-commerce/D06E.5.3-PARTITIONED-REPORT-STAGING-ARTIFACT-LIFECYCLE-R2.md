# D06E.5.3 — Partitioned Report Staging & Artifact Lifecycle

Owner approves temporary PostgreSQL report staging, automatic daily partition creation and partition-level deletion. ## 1. Minimal physical model and ownership
Proposed schema reporting in existing database (name subject to migration/owner inventory). Durable int_report_instance holds tenant, immutable actual parameters/evidence manifest/digest, job and format outcomes or references, artifact references and staging lifecycle metadata; int_report_visibility holds versioned mutable audience policy where existing owner storage cannot support it; int_report_artifact mapping only if existing File Service linkage cannot represent it. Reuse existing registry for definitions, existing file store for binary artifacts and L1/L2/L3 for analytical source. Start with one typed int_report_dataset parent partitioned by staging_date; group/evidence staging parents only if measured row shape/access needs justify them, not mandatory. Staging is disposable, logged PostgreSQL data by default for crash recovery, not SQL TEMP tables, not source of business truth. Keep active Radar/ticket evidence in its existing owner retention, never solely in staging.
Every dataset belongs to one tenant, immutable compatible authorized scope, source revision, method/calendar/parameters and dataset attempt identity. Reuse only identical qualified evidence and compatible authorization; no cross-tenant reuse. Logical dataset identity and attempt/fence in durable metadata; all partitioned PK/unique constraints include staging_date, e.g. (staging_date, tenant_id, dataset_id, row_key), FK/reference design must not obstruct retention or reference disposable rows from durable history. Composite tenant-first lookup within selected day (tenant_id,dataset_id,row_key or stable series/period keys); every read binds date and tenant for pruning and isolation. No per-tenant partitions initially, HASH only on measured need. Separate owner/migration/maintenance privilege from application reader/writer; no unrestricted application DDL. Do not weaken existing authorization/RLS where applicable. No migration or actual tables created in this design change.

## 2. Daily RANGE partition lifecycle (mandatory)
Partition staging_date by UTC calendar date derived once at dataset allocation (not tenant analytical date, report period, or retry date). Tenant calendar/asOf remains in immutable report passport. All rows of a dataset attempt use its allocated date, including retries across midnight. Half-open daily bounds [D,D+1), deterministic trusted names int_report_dataset_YYYYMMDD. UTC chosen to avoid DST and mixed tenant time zones in shared infrastructure.
Automatic maintenance through existing admitted scheduler/worker: at startup/recovery and daily before UTC rollover, ensure current day and next two UTC days exist (initial lookahead proposal, configurable); reconcile missing required dates before admitting new allocation. Use existing distributed singleton/fence or transaction-scoped PostgreSQL advisory lock for partition DDL; validate catalog parent, bounds, indexes and grants, not merely IF NOT EXISTS. Idempotent on multiple replicas and retry; precreate only bounded horizon; no infinite creation or untrusted identifier interpolation. Writer never routes to DEFAULT partition or wrong date. If creation unavailable, fail/retry admission with observable reason, no data loss or silent date substitution. Do not reopen an already retired date; expired attempt must be rebuilt as new allocated attempt under current qualified evidence, not mutate published report.
Maintain partition state OPEN for new allocations, SEALED for no new allocations after UTC day ends (existing pinned writers/readers may finish), RETIRED after safe cleanup. States logical in existing job/maintenance metadata or derived under same database fence; no mandatory new lifecycle service. Catch up missed maintenance after outage, do not use wall clock alone as deletion authorization.

## 3. Retention and deletion exclusively at partition level
Successful report staging: retain at least 24h after durable authorized publication; for shared dataset wait until the last linked consumer has published or reached admitted terminal abandonment. Required formats must have verified owner/file completion, digest, scan and availability before publication; optional format failure only terminal if existing policy admits it. A terminal abandoned/failed attempt may become eligible only after explicit controlled terminal disposition, retry/recovery window and no live consumers; never label it published. Initial abandoned-attempt grace proposal 24h from terminal disposition; bounded retry/lease deadlines and operational escalation prevent indefinite orphan accumulation, but elapsed time alone never deletes active work.
Partition cleanup at daily maintenance: candidate only SEALED dates; all datasets/attempts and consumers in that partition are eligible, no active generation/render/export/upload/retry/recovery/drill read or lease, no unresolved file completion, no legal/operational hold. Use durable metadata, complete reconciliation of staged datasets to lifecycle records; orphan/unknown rows block deletion and alert. Check eligibility and fence new pins/writes atomically using shared coordination with allocation/reader/worker paths. Drain or defer active readers; recheck under lock before DDL. Normal expiration uses DROP TABLE of the verified child partition (or DETACH then DROP only if independently qualified crash-safe); no per-row bulk DELETE, no TRUNCATE shared parent, no CASCADE, no touching L1/L2/L3 or durable report/file metadata. Drop all applicable staging parents for a day only if each is safe; retry idempotently on missing verified retired child. Use bounded lock/statement timeout; busy partition defers cleanup, does not interrupt live work. Audit deletion date, exact parent/bounds, count of datasets if authorized internal telemetry, reason, actor/job/fence and result, without exposing tenant data. Retention is minimum 24h after publication, not exact physical 24h SLA: whole-day eligibility and delayed consumers can retain data longer. Monitor oldest blocked date, disk, orphan count and maintenance failures; backpressure/escalate rather than delete unsafe data.
Example: day D partition has report A published D 08:00 and B D+1 10:00 UTC; earliest eligibility for B D+2 10:00; partition deletion only at subsequent maintenance when every other condition holds. New D+1/D+2 partitions are independent; a delayed report never blocks their creation.

## 4. Artifact and historical detail boundary
Use immutable MicroReportPayload logical contract; staging stores bounded typed rows/series/group/evidence coordinates, no renderer business calculations. Persist qualified dataset under source revision fence, close source transaction, stream staged rows via bounded JDBC reads into trusted Excel/PDF renderer; do not hold analytical snapshot during rendering/upload. Existing job idempotency/lease/fencing controls retries. Publication after actual file scan/attach/digest and report-owner ACL admission (CRM-only current file binding gap remains). Durable report passport, actual data scope, audience policy, artifact references and owner evidence required for authorization/audit survive partition deletion; file retention is separate tenant policy. Never delete file because staging expires. React historical drill-down only if exact authorized retained evidence available; after cleanup return localized unavailable reason or explicit LATEST_DATA new request. Saved XLSX/PDF and authorized exported details remain unchanged. Do not claim old membership digest alone can reconstruct data. No new report format or storage system.

## Atomic dataset handoff (RQ-01/02)
BUILDING/VALIDATING attempt under durable fence; atomically commit complete manifest, row count/digest, scope and revision as READY; only READY may be rendered, immutable thereafter. Retry new attempt; active pins and consumer retention remain mandatory. Monitor blocked dates, disk, counts and create/drop failures; backpressure and alert, no unsafe deletion.
