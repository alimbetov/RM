## CC-01 — Historical coverage evidence
Reuse DataQuality, Coverage, MetricActivityGate and MultidimensionalCoverageService. Existing CURRENT source parity is necessary for qualified L3 but does not prove source history completeness; AuthorizedAnalyticalReadService.result() currently returns PARTIAL/MISSING, including L0 fallback. Never promote by changing enum alone. Minimum immutable evidence:
- tenant, scopeKey, metricCode/methodVersion, source owner and stream, calendar/version, required interval set (half-open UTC instants with tenant calendar), source coverage bounds and authoritative source completeness references, qualified interval set and missing/partial/stale/incompatible reasons;
- revision manifest (source, dirty, receipt, materialization, lifecycle, generation/proof when applicable), actual asOf, policy version, value/qualified-zero proof, applicable unit/currency, visibility scope. No authoritative source proof = PARTIAL/MISSING. Existing owner facts/receipts + independent source reconciliation first; no duplicate coverage ledger unless gap inventory proves necessary and owner admits it.
- qualify exact mandatory intervals, not percentage threshold. Target/baseline/warmup separate; optional history may be partial only if narrower claim declared. Coverage ratio null for empty set; count qualified required intervals only. READY evidence can still be decision BLOCKED. Keep source quality/activity/decision eligibility/publication/ack independent. Test source completeness separately from projection parity. No production historical READY until owner-specific completeness authority and late/import revision invalidation qualified. B4 changes require separate minimal defect approval.

## CC-02 — Bounded authorized dataset
Logical request: tenantId, verified actor/admitted service identity (not fabricated actor), metricCodes, scope keys/filter, explicit required periods, comparisonCode, calendarVersion, asOf mode, page size and continuation. Result: manifest, rows(scopeKey, metricCode, methodVersion, period start/end, nullable BigDecimal value, currency/UOM, quality, reason, evidenceRef), evaluatedScopeCount and scanComplete, continuation. Scope key canonical sorted stable IDs, geography and product axes independent; include historical-only scopes when eligible. No Cartesian generation.
Single tenant per request, authorize before enumeration/count/read, fresh owner fences at publication/download. Keyset pagination with stable sort; revision manifest pin across pages, restart on drift, never claim multiple transactions are one MVCC snapshot. Existing 12 anchors/3 metrics/100 warehouses limits remain for legacy factor path. Bulk path set-based bounded reads; initial internal target 24 closed monthly slots per row and explicit extra lookback only when method requires. Batch size proposal 100 series/page and ≤2400 points for 24M; lower dynamically for lookback/resource budget; existing PostgresDerivedWindows max 1000 series and 12000 points is a separate numerical kernel limit, not authorization. Test query count scaling by batch, no metric×scope×period N+1. No arbitrary SQL, no uncontrolled L0 fallback fanout, budget exhaustion explicit incomplete scan. Exact distinct computed at target grain, never sum warehouse or time distinct. 100 warehouse cap cannot be bypassed by summing distinct over pages.

## CC-06/07 — Pattern and information tickets
Logical PatternTicket: stableKey = canonical tenant + scopeKey + metric set (ordered where semantic roles differ) + patternCode/version policy identity + comparison basis + episode/period identity; occurrenceDigest = canonical evidence revision/values/required intervals/method/policy/quality; observation, delta, relative result, evidence refs, asOf, eligibility. Persist only positive findings and needed lifecycle/evidence, diagnostics aggregated separately; no record for every failed candidate. InformationTicket uses existing Radar provider/identity after admission: stable situation key, primary affected scope, linked qualified patterns, localized typed args, revision digest, quality, materiality, optional admitted check, state. Exact same situation compatible scope/period dedup, no additive double counting, no suppression of child by parent. Episode identity policy: same closed comparison period or same intraday business day and condition = same logical episode; distinct period is separate candidate, not automatic re-notification; cross-period grouping and recurrence policy require Radar owner review.
Logical transitions: candidate → qualified → published only after gates; repeated semantic result no duplicate; changed evidence supersedes under revision fence; missing/stale evidence → STALE/UNKNOWN not RESOLVED; qualified disproof → RESOLVED; recovery reuses identity; revoke hides, not resolve. User acknowledgement independent. What Changed compares compatible admitted manifests, no update from rendering timestamp alone. No risk count from data-quality notice; no active recommendation when decision BLOCKED. Reuse existing owner/audit/storage; physical schema only after inventory.
