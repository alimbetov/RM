# RM P4.1 — Confidential Report File Protection

Date: 2026-11-28. Design handoff against base_dev 7b1cf1efe0560cfd90be4969e72e4b923786bd0b; P4 guard candidate d69daea7218d206ed47bb42f30e7b84a21d49d43 (not integrated).
Status: implementation contract, qualification pending. P4.0 fresh SHA admission precedes implementation in base_dev. No production admission.

## 1. Scope and precedence

Narrow exception to the FILES 2026-11-21 no-application-encryption decision: NEW server-generated CONFIDENTIAL REPORT XLSX/PDF must use authenticated binary encryption from first persistent byte, including staging, temporary spool and final object. Existing INTERNAL/BUSINESS_PUBLIC_CANDIDATE and legacy format-0 files remain unchanged; no automatic migration, no production admission of other confidential files. The exception becomes operative in base_dev only with the qualified implementation and synchronized FILES policy documentation. Do not remove the guard or label plaintext as format 1. Existing PII encryption, file provider selection, KMS deployment restrictions, AV and report ownership contracts remain. No new service, scheduler, bucket, storage engine or table by default. Any necessary additive schema constraint must be justified against actual schema; never edit applied migrations.

## 2. Trusted upload and file content contract

- Renderer-owned internal REPORT upload intent only, not a generic client MIME allowlist expansion. Require VerifiedActor, tenant, FILES_UPLOAD and REPORT_GENERATE; full report scope is authorized by INTELLIGENCE. Bind intent to immutable instance, format, renderer/dataset passport, requester and idempotency key; reject conflicting replay. A scheduled actor requires separately admitted single-tenant service identity and current requester scope, not an invented user.
- Classify CONFIDENTIAL on creation, immutable through completion. XLSX cap 2 MiB, PDF cap 25 MiB (initial engineering caps aligned with candidate gate; verify renderer and transport). Validate declared length, SHA-256 of original bytes, exact MIME, PDF signature/structure as appropriate, and actual OOXML package structure for XLSX: required workbook/content types/relationships, bounded inflated size/entry count/ratio, no traversal, duplicate entries, macros or external relationships. ZIP magic alone is insufficient. AV scans precisely the authenticated original bytes, not ciphertext; timeout/error/infected fail closed. No plaintext file or spool on persistent storage.
- Extend the existing FileStoragePort and SwitchableFileStorage consistently; provider-independent authenticated content codec, no second file pipeline. Stage with ciphertext only; scanner reads bounded authenticated plaintext from encrypted staging, final promote retains identical immutable ciphertext (or verifies authenticated content and binding). Revalidate final bytes and expected hash before AVAILABLE. Persist version 1 only after actual encrypted write and verification. Metadata size_bytes and sha256 retain ORIGINAL plaintext semantics; physical ciphertext length is separate and never compared to original length. Legacy version 0 behavior unchanged.
- All paths must understand envelope version: upload/finalize, already-AVAILABLE retry, scan, promote, matches, authorized binary read, reconciliation and quarantine. Unknown versions, missing KMS, key or corrupt envelope fail closed; distinguish temporary infrastructure unavailability from proven corruption (do not quarantine on transient outage). Bind verification to exact immutable object reference and file row version; no storage keys exposed to clients.

## 3. Binary cryptography — bounded initial profile

Introduce internal FileContentCryptoPort in existing KMS boundary (not String/base64 via TenantCryptoPort, no exported DEKs). Reuse tenant key generation selection, root wrapping and historical generation lookup. Initial profile: one AES-256-GCM authenticated envelope per bounded report file; no custom cipher. Derive a dedicated per-upload encryption key from the existing tenant DEK using HKDF-SHA-256 with fresh cryptographic random salt and domain-separated info (RM:FILES:REPORT:v1, tenant ID, file ID, immutable upload attempt identity, generation). Fresh nonce per encryption; never reuse an envelope identity with different bytes. Preserve key generation and salt/nonce in versioned bounded header. Canonical length-prefixed authenticated header/AAD binds version, tenant ID, file ID, upload attempt, generation, format, original size and SHA-256; reject noncanonical/unknown fields, malformed lengths and trailing bytes. Define byte layout and independent golden vectors before implementation. Do not share the string cipher nonce domain or use root key directly for content. No raw key material crossing KMS boundary.

The 25 MiB upper bound allows authenticate-before-release using bounded in-memory buffers; no unverified plaintext goes to scanner or HTTP sink. Budget all simultaneously held plaintext/ciphertext buffers and parser/renderer expansion with global and per-tenant weighted concurrency admission, bounded queue/timeouts, fail closed on overload. No unlimited heap or plaintext disk fallback. Test memory under load; if cap is insufficient, separately qualify chunked authenticated format, not implicit format-1 change. Clear sensitive buffers where feasible, forbid payload/key logging and heap dumps in production. KMS rotation/migration remain disabled per KmsDeploymentGuard; multi-pod read/write with immutable generations and backup/restore must be qualified before production. No claim of secure erasure of JVM heap.

## 4. Atomic publication interface

P4.1 supplies a verifiable encrypted FILES artifact, not publication itself. The existing candidate ReportFilePublicationGate is retained/rebased after P4.0; positive path requires actual version-1 artifacts, not SQL-forged flags. Complete owner adapter and publication in P4.2 using existing report_instance/int_report_consumer schema as actually implemented: IAM/current whole scope -> instance/visibility -> consumer -> sorted file locks. Compare immutable staged manifest and exact verified reference/version, required formats, current owner, CLEAN/AVAILABLE/ACTIVE, size and digest. Never perform full object I/O under SQL locks; trusted verification receipt must be bound to immutable object identity and checked under locks, with protection from replacement and GC. Persist REPORT attachment and immutable publication receipt with consumer CAS in one short transaction; ACK and cleanup remain separate under existing lifecycle lock protocol. Retry returns only exact committed receipt with fresh authorization; different payload or owner fails. No catalog visibility before successful publication. Read through authenticated RM service, no public or presigned GET for confidential artifacts; verify full content before releasing plaintext and recheck access at download start. Already-downloaded bytes cannot be revoked.

## 5. Admission matrix

- Existing FILES format-0 regression for LOCAL/RustFS, CRM and public media; no change in global flag behavior.
- Actual XLSX/PDF encrypted stage/final objects, positive scanner + decrypted hash round trip on real RustFS; inspect raw stored bytes and spool; synthetic scanner only in test profiles. Wrong tenant/file/attempt/generation/format/AAD, changed tag/header/ciphertext, truncation, trailing bytes, forged metadata, malformed OOXML/zip bomb, key unavailable, AV timeout/infection, no leaked plaintext.
- Idempotent upload, wrong payload replay, competing pods, fencing on stale upload, crash before/after final object and DB commit, recovery with exact immutable reference; no false AVAILABLE and no deletion of committed object. Distinguish integrity failure from retryable storage/KMS outage. Authorization revoked before commit/download, within-tenant scope isolation. Positive and negative independent crypto vectors, memory/backpressure, real PostgreSQL and RustFS/ClamAV qualification, backup/restore and exact SHA evidence.
- P4.0: SALES + Development Admission + Exact-SHA GREEN for fresh base_dev SHA, no rerun-provenance bypass. P4.1 implementation and P4.2 publication require new exact-SHA qualification; P4.3/4.4 delivery/catalog and independent P4.5 audit remain open. 12/12 XLSX template generation is not proof of confidential publication.
