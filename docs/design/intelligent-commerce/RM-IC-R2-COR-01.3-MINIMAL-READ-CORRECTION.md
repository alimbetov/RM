## What is actually wrong and what is not
AuthorizedAnalyticalReadService.readMetricWindows admits each metric in outer READ COMMITTED (TenantAuthorization.requireForCommand MANDATORY, actor/workspace SHARE, warehouse scope where applicable). Inner REQUIRES_NEW is a read-only REPEATABLE_READ transaction. All queries/anchors share tenant, calendar, period code and relevant scope; currency can differ across metrics. readSnapshot resolves period, reads source revision and ACTIVE pointer, calls coverage.statusInSnapshot for eligible closed periods. That status checks the transaction isolation then evaluate re-runs five independent parity checks when stored proof revisions and zero counters match. IndependentCanonicalDigestVerifier.mismatches reads all tenant facts; a valid SALES fact requires event/header/line queries; INVENTORY one movement query. This is an N+1 verification inside the existing request, not a second engine. On a valid closed window the same generation-wide check repeats up to 36 times (3 metrics * 12 anchors), not measured latency or SQL count. Short-circuit failures may do less. Existing L3 readPeriods is set-based but the authorized route calls it with one period. Current historical results remain PARTIAL/MISSING, including valid L3. No historical readiness is implied.

## Trust and lock review
MultidimensionalCoverageService.activate uses existing workspace FOR UPDATE, pointer lock and lifecycle FOR UPDATE NOWAIT, re-evaluates BUILDING proof, copies verified counters into a new lifecycle-bound ACTIVE proof and atomically switches pointer. Preserve activation, rollback and replay. DDL source revision triggers cover inserts of events, lines, movements, canonical facts, dimension rows; append-only revision event journal. L2 BUILDING-only mutation, dirty revision, receipt revision, L3 period/cell/membership guards and materialization revisions; reservation revision trigger; immutable/no-truncate proof rows. This is source inspection, not exhaustive bypass/privilege proof. Revision is tenant-global; do not add targeted invalidation or assume all possible mutations covered.
Existing synthetic rm_dim_proof_gate NOLOGIN may SELECT/INSERT proof, cannot modify source/revisions or activate; ordinary role forgery negatives exist. Writer can still insert arbitrary zero counters; privilege separation is not proof of correct computation. No actual deployment identity/grant inventory found in inspected app configuration (dev/test datasource; no application-prod.yml in resources); DB access unavailable. Therefore no cross-request reuse of persisted proof based only on revisions, no removal of evaluate's independent oracle. Existing B5.5 revocation/concurrency and activation/forged proof evidence retained. Source recovery did not revert 0222/0223 on deployed databases; actual applied changesets remain unverified; do not deploy recovered source against affected databases without separate compatibility approval.

## Smallest candidate (COR-01.4 / first implementation only after owner acceptance)
Change only AuthorizedAnalyticalReadService's existing snapshot-local execution. Create a local Map keyed by tenant, generation and proof (all in same immutable PostgreSQL RR snapshot; key may include revision for clarity). Pass it to readSnapshot, computeIfAbsent only at the existing coverage.statusInSnapshot call. No shared fields, static cache, TTL, Redis, table, scheduler, new service, or altered DB role. Cache all returned statuses only within that single snapshot; exceptions propagate, do not cache across calls. Authorization, future/open/outside checks, per-anchor period stamps, fallback L0, reasons, quality, result order and bounds unchanged. A later transaction always independently verifies again; stale/forged proof still rejected by full existing oracle. No change in activation, proof writer, historical coverage, zero semantics or public API. This is request-local deduplication, not a trusted persisted proof design. If current one-snapshot premise changes, remove/review reuse.
Why first: reduces repeated whole-tenant checks from up to 36 to one per distinct proof in an admitted window, without weakening trust. Does not remove one full verification or N+1 cost and does not make 24-month reports admitted. Do not batch/change readPeriod routing simultaneously. Reuse set-based readPeriods as a later bounded improvement only if evidence justifies it; no broadened limit. Persisted trusted proof optimization and history completeness are separate open decisions, not required for this small correction.
