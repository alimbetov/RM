# RM-I18N-R1 — Единый стандарт четырёхъязычности модульной CRM

**Статус:** PROPOSED / на согласование.
**Языки:** `kk` (қазақша), `ru` (русский), `en` (English), **`zh-Hans` (简体中文, упрощённый китайский)**.
**Назначение:** единая локализация интерфейсов, справочников, сообщений, коммерческих документов и коммуникаций для всех модулей RM.
**Ссылки:** [аудит](../reviews/RM-I18N-R1-AUDIT-2026-11-21.md), [модульное ТЗ](RM-MODULAR-DOMAIN-DB-R1.md), [партиционирование](RM-PARTITIONING-R1.md).
**Не входит в данный шаг:** реализация полного UI, машинный перевод, переименование текущих таблиц, изменение KMS или создание партиций.

## 1. Принципы

1. **Одна бизнес-сущность, три языка.** Не создавать `crm_customer_ru`/`crm_customer_kk`/`crm_customer_en` и не партиционировать таблицы по языкам.
2. **Структурированные данные не переводятся**: UUID, tenant, KATO Code, SKU, даты, валюта, суммы, статус-код, коды ошибок, криптографические ключи.
3. **Тексты интерфейса переводятся через resources**; tenant-editable каталоги товаров, услуг, категории, шаблоны — через module-owned `*_i18n` (для изменяемых и независимых языковых редакций).
4. **Четыре языка поддерживаются в продукте**, но факт заполнения переводов для контента организации не гарантируется. Не требовать обязательного заполнения всех четырёх языков при каждом добавлении товара; хранить базовую локаль и применять определённый fallback.
5. **Нет автоматического перевода персональных данных**. ФИО, свободный текст, адрес контакта и документы клиента сохраняются в исходном виде и защищаются KMS, если содержат PII.
6. Английские подписи КАТО из `NameRus` — **латинская транслитерация**, не перевод и не официальное английское географическое наименование.
7. **Locale и регион независимы.** `region_zone_id` из КАТО не определяет язык, `tenant_id` не кодирует страну или язык.

## 2. Код языка и fallback

- Языковые коды: lowercase BCP-47 language subtag `kk`, `ru`, `en`. Вход `kk-KZ`, `ru-KZ`, `en-US` приводится к поддерживаемому `kk`/`ru`/`en`/`zh-Hans` после корректного BCP-47 parsing; неизвестные/некорректные tags — к безопасному fallback без выполнения пользовательского кода.
- Язык интерфейса: явный выбор пользователя → `UserPreference.preferredLocale` → `Accept-Language` → default `ru` (продуктовая начальная конфигурация; менять можно независимо от данных). Явная смена языка сохраняется в предпочтении пользователя после авторизации.
- Язык контента организации: запрошенная locale → `entity.sourceLocale` и исходный текст → `ru` fallback, если существует. Ответ должен включать `requestedLocale` и `resolvedLocale`, чтобы потребитель различал отсутствие перевода от настоящего перевода.
- Для **критических документов, согласий и рассылок** fallback на непроверенную локаль запрещён: нужен явно опубликованный и утверждённый текст на выбранном языке или сознательно выбранный пользователем язык документов.
- Если поле отсутствует в доступных языках, показывать исходное имя и метку отсутствия перевода; не подставлять пустую строку, не генерировать машинный перевод без отдельной функции и согласования.
- UI переключает язык без изменения `tenant_id`, `customer_id`, `sku`, `region_zone_id` или содержимого сохранённых договоров.

| Модуль | Что локализуется | Хранение |
|---|---|---|
| IAM | системные роли/приглашения/ошибки; `preferred_locale` | resource bundles + preference, не переводить OIDC subject |
| ORG | тип организации, статус, элементы UI | ресурсные сообщения; фирменное/юридическое наименование как исходные данные, без самовольного перевода |
| GEO | `NameKaz`, `NameRus`, `NameEng` (транслитерация) | текущие поля `name_kk/name_ru/name_en` в одном справочнике |

| CRM | тип клиента, статусы, названия полей и ошибки; согласия | resources; сам текст утверждённого согласия версионируется по языку, контактный PII не переводить |
| CATALOG | категории, названия товаров/услуг, описания, характеристики | `cat_category_i18n`, `cat_item_i18n` c owner tenant |

| INVENTORY | названия статусов и типов движений, складские формы | resources; складское имя — бизнес-данные, допускается `org_location_i18n` по реальной потребности |
| FINANCE | счета, статусы, подписи, платёжные документы | resources и версионированные шаблоны PDF по языкам; суммы/валюты не меняются |
| MARKETING | шаблоны email/SMS, campaign messages, unsubscribe тексты | `mkt_template_i18n` + version/published state по locale; consent перед отправкой |
| TASKS | статусы, приоритеты, нотификации | resources; тело задачи/переписки не переводится автоматически |
| AUDIT | отображаемые подписи действий по стабильному `action_code` | resources, исходный audit event не переписывается |
| KMS | пользовательские error codes и безопасные сообщения | resources; ключи и crypto context не локализуются |
| SUBSCRIPTION | названия планов и описания entitlements | resources либо `sub_plan_i18n` для редактируемых продуктовых текстов |

## 4. База данных и таблицы с префиксом модуля

### 4.1. Лёгкие системные справочники

Для небольшого КАТО оставляем `name_kk`, `name_ru`, `name_en` — это эффективно и уже существует. В интерфейсе `Code` скрыт, но остаётся техническим ссылочным значением.

Дополнительно можно хранить `name_en_kind = TRANSLITERATION` логически или в будущей миграции, чтобы не выдавать техническую запись за официальный английский перевод.

### 4.2. Организационные переводимые данные

Пример CATALOG (новые таблицы в будущем, не исполняемый migration):

```sql
CREATE TABLE crm.cat_item (
    tenant_id UUID NOT NULL,
    id UUID NOT NULL,
    source_locale VARCHAR(2) NOT NULL,
    sku VARCHAR(80) NOT NULL,
    status VARCHAR(24) NOT NULL,
    PRIMARY KEY (tenant_id, id),
    UNIQUE (tenant_id, sku)
);

CREATE TABLE crm.cat_item_i18n (
    tenant_id UUID NOT NULL,
    item_id UUID NOT NULL,
    locale VARCHAR(2) NOT NULL,
    name VARCHAR(240) NOT NULL,
    description TEXT,
    PRIMARY KEY (tenant_id, item_id, locale),
    FOREIGN KEY (tenant_id, item_id)
       REFERENCES crm.cat_item(tenant_id, id),
    CHECK (locale IN ('kk','ru','en','zh-Hans'))
);
```

Тот же шаблон `cat_category_i18n`, `mkt_template_i18n` и другие module-owned translations, когда их действительно нужно независимо редактировать. **Не вводить одну центральную `translations(entity_type,entity_id,...)` для всех модулей**: она лишает базы нормальных FK, приводит к междоменным зависимостям и проблемам tenant-scoping.

Индексы: PK `(tenant_id, entity_id, locale)` обеспечивает точный lookup. Для полнотекстового поиска по языкам отдельный индекс/поисковая конфигурация только после измерения нагрузки; **locale не входит в ключ партиционирования**. Префикс `cat_` сохраняется.

### 4.3. Стабильные документы

Для принятых смет/заказов фиксировать `locale_at_acceptance`, `name_snapshot`/`description_snapshot` как фактически согласованный текст, `template_revision_id`, `created_at`. Новый язык UI не переписывает принятый документ. При необходимости сформировать новую языковую печатную версию — отдельный документ/артефакт с неизменяемой связью с исходным коммерческим документом.

При необходимости двуязычный договор — отдельная утверждённая версия, не простой fallback.

## 5. REST / сервисные контракты

- `Accept-Language` выбирает язык **представления**, а не физические таблицы. Для ответа со словарём можно передать `?locale=kk|ru|en|zh-Hans` при явном API-договоре; не дублировать многочисленные конфликты priority.
- Возвращать `Content-Language` для реально выбранного языка результата; для fallback полезны `requestedLocale` и `resolvedLocale` в DTO, если есть content translation.
- Тексты ошибок локализуются, но `errorCode` стабилен; HTTP status не зависит от языка. Не включать PII в ошибки.
- `LocaleResolver` и message resources с гарантированным UTF-8: `messages_ru.properties`, `messages_kk.properties`, `messages_en.properties`, `messages_zh_Hans.properties`; проверка missing keys в CI.
- Денежные суммы и даты внутри API хранятся/передаются нормализованно (`BigDecimal`, ISO 8601 timestamps, `currency`), UI форматирует по locale. Не передавать локализованную строку `1 200,50 ₸` в поле, предназначенном для числового значения.
- Запросы на запись контента явно задают `locale` и валидируют её из allowlist; для изменений опубликованных templates — новая revision, а не silent overwrite.

## 6. Безопасность

- Переводная строка тоже может содержать персональные данные или вредоносный HTML; sanitize/escape, RBAC по tenant, ограничения размеров.
- CRM PII (фамилия, контакты, частные заметки, документы) не помещать в `cat_*_i18n`, audit, поисковую строку или общий кэш. Изменение языка UI не даёт права decrypt.
- Кэш справочников (при необходимости) ключуется `tenant_id + entity_id + locale + revision`; глобальные справочники — `code + locale + sourceVersion`. Кэшировать расшифрованный PII без отдельного криптографического допуска нельзя.
- Для файлов указывать locale только у языковых артефактов (например PDF счёта), не шифровать и не партиционировать файлы по языкам.
- Полные переводы маркетингового сообщения должны быть опубликованы/утверждены; отписка работает на всех языках для того же `tenant_id/contact_id/purpose`.

## 8. Acceptance matrix

1. Все системные message keys доступны для `kk`, `ru`, `en`, `zh-Hans`; missing keys = CI failure.
2. В GEO одна и та же территория разрешается на четырёх языках, `Code` постоянен, `NameEng` явно маркирован как transliteration.
3. Переключение locale в UI/API не изменяет `tenant_id`, цену, `region_zone_id`, UUID, статус или количество.
4. CATALOG: перевод товара `kk` и `ru` принадлежит тому же `tenant_id`; коллизия `(tenant_id,item_id,locale)` отклоняется; два разных tenants могут иметь одинаковые SKU.
5. Отсутствующий перевод -> source locale с явным указанием actual locale; никаких пустых/случайных переводов.
6. Контакт/документы с PII остаются зашифрованными в базе; auditor не получает decrypt по смене языка.
7. Сметы и счета, принятые на языке A, остаются в исходной ревизии после изменения языка карточки на B.
8. Маркетинговое сообщение не отправляется при отозванном consent или отсутствии утверждённого языка; unsubscribe не зависит от locale.
9. Казахские Unicode-символы, латиница, HTML-escape, CSV/XLSX/PDF с корректными шрифтами проходят E2E.
10. Индексы `(tenant_id,entity_id,locale)` и текущий partitioning plan не ломают клиента между несколькими регионами.
11. H2 smoke + PostgreSQL integration и browser E2E (когда есть UI) обязательны по мере реализации; данное ТЗ не утверждает, что эти тесты уже проведены.

**Заключение:** четырёхъязычность — базовый сквозной контракт модулей RM. Нельзя считать поддержку `en` законченной только по латинской транслитерации КАТО.

## 9. Поправка I18N-R1.0A — упрощённый китайский

**Продуктовое решение:** четвёртый поддерживаемый язык — `zh-Hans` (упрощённая китайская письменность), а не общий `zh` и не `zh-Hant`. Канонический BCP 47 tag API/БД — `zh-Hans`; Java resource bundle использует `zh_Hans`. Поддерживаемый вход `zh-CN`/ `zh-SG` может нормализоваться в `zh-Hans` через явную allowlist; `zh-TW`/`zh-Hant` **не** транслировать в упрощённый китайский автоматически — применять согласованный fallback и показывать фактическую локаль.

**Важная корректировка модели:** `locale VARCHAR(2)` недопустим для `zh-Hans`, минимум `VARCHAR(12)` с CHECK на поддерживаемые BCP-47 значения. Это относится к `*_i18n.locale`, `source_locale`, `preferred_locale`, `document_locale` и `template_locale`. Новые SQL changesets нельзя создавать со старой длиной.

- **GEO КАТО:** текущие `name_kk`, `name_ru`, `name_en` сохраняются; `name_en` — романизация RU. Для китайского в будущем добавить `name_zh_hans` (nullable) **только из проверенного источника перевода или редакционного утверждения**, либо использовать переводимые записи `geo_kato_i18n` с `locale=zh-Hans` при появлении более широких языков. Пока таких данных нет, выдавать явно помеченный fallback `ru` либо `en` по выбранной продуктовой политике; не транслитерировать русский автоматически в китайское название.
- **CATALOG:** `cat_category_i18n`, `cat_item_i18n` поддерживают `zh-Hans`; SKU/цена/остаток не зависят от локали. Поиск китайского текста требует отдельного квалифицированного анализатора; не обещать полноценную сегментацию китайских слов обычным PostgreSQL full-text config без тестов.
- **MARKETING/LEGAL:** `mkt_template_i18n`, согласие и документы — только после утверждения китайской редакции. Недоступная локаль не приводит к автоматической отправке текста на другом языке без явного подтверждения.
- **UI:** проверить CJK шрифты и перенос строк, ввод и иероглифы в PDF/Excel/файлах, `zh-Hans` локаль отображения даты/денег; китайские текстовые строки не переводят юридические названия и PII сами собой.
- **Качество:** контрактные тесты для всех четырёх языков, fallback, отсутствие транслитерации вместо перевода, отсутствие коллизий в `(tenant_id,entity_id,locale)`; сборки H2/PostgreSQL, документные QA.
- **Нет новых языковых партиций или отдельных схем.** Модульные префиксы и `tenant_id` сохраняются.
