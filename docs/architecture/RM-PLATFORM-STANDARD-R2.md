## 1. Назначение и продукт

RM — **CRM-first business platform**: единая рабочая среда организаций для управления клиентами, взаимодействиями, продажами, исполнением заказов, складом и последующим обслуживанием. Сопутствующие функции — финансы, маркетинг, задачи, файлы, аудит, безопасность, подписки и витрина продавца — остаются отдельными контекстами.

Нормативная бизнес-цепочка для проектирования: **клиент → взаимодействие/предложение → заказ → исполнение → оплата → дальнейшее обслуживание**. Наличие звена в концепции **не означает**, что оно уже реализовано. CRM не должна напрямую изменять складские остатки, финансовые проводки или состояния заказа в обход соответствующего домена.

**Принципы:** простота до подтверждённой необходимости, сквозной рабочий сценарий вместо CRUD ради CRUD; явные контракты, целостность данных, проверяемая безопасность, локально понятные решения.

## 2. Технологическая основа и нецели

- **Java 21; Spring Boot 4.1.3; Spring MVC; Spring Data JPA/JDBC** по назначению; **PostgreSQL** — целевая транзакционная БД; **H2** — совместимость/тесты; **Liquibase formatted SQL** — версионные изменения схемы.
- **Один модульный монолит**, один deployable artifact; домены отделены пакетами, сервисными контрактами, схемой данных и тестами.
- В текущем этапе **не вводить** микросервисы, Redis, отдельный authorization/policy-engine, универсальный workflow-engine, динамический язык правил, наследование ролей, вложенные группы, тотальное разделение на DTO/Repository для каждого объекта.
- Caffeine и иные кэши допустимы только для подтверждённых read/crypto-задач, **не как источник истины об активных полномочиях**. Не утверждать немедленный отзыв прав по TTL кэша.
- Новая инфраструктура, таблица или абстракция допускается при конкретном пользовательском сценарии, требовании безопасности или измеримой проблеме производительности.

## 4. Идентичность и tenant

- Один глобальный `userId` для физического пользователя, одна связь с внешним OIDC subject; пользователь может входить в несколько организаций.
- **Профиль IAM — глобальный, не tenant PII.** Email и профиль пользователя нельзя шифровать DEK одной организации. Существующие `iam_email_identity.email_envelope/lookup_hmac` уже защищают глобальный email; `iam_user_account.display_name/email_normalized/phone_e164` пока могут храниться открыто. Их миграция регламентируется §25.
- **`tenantId = iam_workspace.id`** для организационных данных. `organizationId` — бизнес-сущность организации, не `tenantId`. Склад, филиал, KATO/регион, проект и профиль клиента **не являются** самостоятельными tenant по умолчанию.
- Пользователь явно выбирает рабочую организацию, но **любой указанный tenantId проверяется сервером** по активным account, workspace, membership; нельзя принимать доверие к tenant/actor из HTTP body/query.
- Операции другого tenant и чтение чужих идентификаторов — **deny by default**, включая вложенные JOIN, поисковые запросы, файлы, экспорт, фоновые задания.

## 5. Единственная модель авторизации

### 5.1 Три независимых условия

1. **Identity admission** — доверенный `VerifiedActor` из проверенного токена (issuer, audience, signature, expiry, subject; реальные HTTP/OIDC/BFF ещё не допущены).
2. **Tenant functional RBAC** — активная организация + членство + конкретное `DomainPermission` через назначенную активную функциональную роль.
3. **Object/business policy** — принадлежность объекта tenant, допустимая область видимости, состояние объекта, согласие, лимит или утверждение. **RBAC grant не отменяет проверки объекта.**

### 5.2 Роли и permissions

- `OWNER` в membership — **неделегируемое** право `TENANT_RBAC_MANAGE` и восстановление управления организацией по утверждённому процессу; **не wildcard на все бизнес-операции**.
- Организация самостоятельно создаёт и комбинирует роли вроде директора, менеджера, кладовщика, бухгалтера. Роль принадлежит одному tenant; пользователь может получить несколько ролей; эффективные permissions — объединение grants **активных** ролей в том же tenant.
- Каталог **допустимых** permissions принадлежит коду (`DomainPermission`); пользователь не может создавать новый permission или назначать `TENANT_RBAC_MANAGE` через tenant role. Не строить hardcoded роль на каждый домен.
- `PLATFORM_ADMIN` — отдельная глобальная операционная привилегия. Она **не означает** автоматическое чтение CRM, PII, заказов или доступ к KMS tenant.
- До явной активации `iam_tenant_rbac_config.enforced` действует только документированная совместимость SEC-R1.0; новые бизнес-write права **не открываются** по умолчанию. Включение tenant RBAC требует предварительно назначенного работающего permission, отдельной проверки и аудита.
- Успешная авторизация одной части операции не даёт права на другую: SALES confirm + INVENTORY reserve проверяются парой в одной транзакции.

### 5.3 Область доступа к объектам — политика домена

CRM решает видимость клиентов/контактов и раскрытие PII; SALES — заказов/предложений; INVENTORY — складов/SKU; FILES — владение файлом и скачивание; MARKETING — действующее согласие; FINANCE — право финансового утверждения. Каждое решение **исполняет владеющий домен**, не универсальный engine.

**DECISION REQUIRED перед расширением:** все склады tenant или назначенные; весь CRM-портфель или закреплённые клиенты; все заказы или личные; условия двойного утверждения на критичных корректировках/финансах. Пока нет утверждённой политики, **не обещать** такой доступ и **не расширять** права по умолчанию. Не внедрять ABAC/framework заранее.

### 5.4 Отзыв и административные изменения

Команда изменяющего сервиса получает транзакционный допуск через `TenantAuthorization.requireForCommand`; политика блокировок PostgreSQL должна исключать пересечение зафиксированного отзыва с уже допущенной изменяющей командой. Тот же порядок блокировок обязателен для изменения ролей, membership, account и workspace; отказ/rollback проверяются двухсоединительными PG-тестами, включая stale JPA state.

В `main` реализованы tenant/RBAC role barrier, account/member/tenant lifecycle, actor-row locking и защита от stale JPA из PR #4. Это квалифицированное внутреннее ядро, **не** реальная HTTP/OIDC-граница и не production security approval. Восстановление заблокированной организации — отдельный доверенный admin-path, а не обход всех обычных команд.

## 6. Доменные границы и пользовательский процесс

- **IAM:** регистрация `emailVerified=false`; подтверждение конкретного адреса — только после one-time proof. При смене email старый адрес остаётся текущим до подтверждения нового. Статус почты не равен OIDC-login или tenant permission; подробнее §25.
- **CRM:** создание/поиск клиента и контакта, история взаимодействий и согласий, ответственное лицо; PII раскрывается только после отдельного `CRM_PII_READ`. Создание контакта не означает согласие на рассылку. Полнота портфеля/назначений — отдельный контракт.
- **SALES:** от коммерческого предложения/заказа к подтверждению, отмене и исполнению. Один seller tenant на заказ; фиксировать цены/состояния и сохранять историю. `COMPLETED` в текущей реализации нельзя автоматически трактовать как подтверждение доставки, оплаты или финансового закрытия.
- **INVENTORY:** склад/позиция → поступление → доступный остаток → резерв → выдача/списание → неизменяемое движение. `available = on_hand - reserved`, `on_hand >= reserved >= 0`; причина коррекции, requestKey и audit обязательны.
- **FINANCE, MARKETING, TASKS:** развиваются собственными вертикалями и используют документированные связи с клиентом/заказом, без прямых SQL-изменений чужих aggregate.
- **STOREFRONT/public:** публичные просмотры и оформление не требуют фиктивной роли сотрудника. Отдельная public policy: anti-abuse, ограничение раскрытия данных, идентификация покупателя где требуется.

## 7. Сервисы, транзакции, данные

1. Публичная граница приложения получает проверенную identity, валидирует вход, проверяет permission + tenant + объект, затем вызывает доменную команду. Транспорт и REST контроллеры не входят в текущую стабилизацию.
2. Каждая business mutation атомарна в PostgreSQL; для междоменных SALES/INVENTORY изменений один orchestration service и одна транзакция. Никаких прямых вызовов незащищённых raw `adjust/reserve/fulfill` из других контекстов.
3. Повторяемые команды: явный idempotency key, неизменяемый результат, другой payload с тем же ключом — ошибка. Операции над запасами защищаются row locks, проверками переходов состояний и уникальными индексами. Никаких отрицательных или скрыто двойных списаний.
4. Tenant ownership выражать `tenant_id` во всех predicates и по возможности composite PK/FK. Исторические физические имена таблиц (в том числе `crm.sales_order`) могут оставаться до **проверенной** миграции; не переименовывать ради красоты.
5. При изменении схемы только **новые Liquibase changesets**; применённые не переписывать. Не удалять реальные записи клиентов, бухгалтерские данные, события/аудит и старые migrations ради документационной чистоты.
6. Для пользовательских списков — ограниченная пагинация, стабильный порядок, серверная tenant фильтрация; COUNT и PAGE в разных запросах не дают консистентный export-snapshot. Файлы/PII/экспорт имеют собственные объектные проверки.
7. История значимых бизнес-операций и изменений прав — append-only; исправление ошибочной записи новым событием. Не писать секреты, токены, расшифрованные PII в логи и audit. Ключи KMS не являются обычными правами `OWNER`.
7a. **PII-by-default:** перед сохранением каждого нового личного поля указать владельца данных (global IAM или tenant CRM), режим шифрования, AAD, lookup-index, права расшифровки, миграцию/retention и negative tests. Ни JPA Entity, ни DTO, ни audit не становятся обходом PII-границы; существующие legacy plaintext IAM-поля должны исчезнуть после доказуемого cutover R2.5.
8. Системные задачи/воркеры получают ограниченную service identity и явный tenant context. Не использовать «универсального системного пользователя» с доступом ко всем данным.

## 9. Порядок разработки R2

1. **R2.0 IAM:** завершить P0/security gaps, полноценный отзыв доступа, reviewer sign-off, exact-HEAD CI; затем merge.
2. **R2.1 INVENTORY:** приёмка позиции/склада, поступление, корректировка, остатки, движения, резерв, история — один завершённый путь кладовщика.
3. **R2.2 SALES:** заказ/строки, подтверждение, резерв, отмена, исполнение, история — один завершённый путь менеджера и склада; не смешивать с оплатой/доставкой без отдельного решения.
4. **R2.3 CRM:** клиент/контакт, поиск, PII, согласие, назначение/история — один завершённый путь CRM-оператора.
5. После квалификации — доверенные transport adapters, реальные OIDC сессии и следующие домены по бизнес-приоритету.

Новых крупных платформенных компонентов **не вводить** без доказанной необходимости.

## 10. Иерархия документов и изменение стандарта

**Этот документ — единственный нормативный источник архитектурных и security-правил RM-R2.** `README.md` — навигация и краткий статус; `DomainModule`, код, тесты и миграции — доказательство **фактически реализованного**; спецификации доменов/ADR — детализация; `docs/reviews` и прежние версии ТЗ — исторические evidence с указанным SHA, не параллельные нормативные стандарты.

При конфликте «стандарт vs код» **не утверждать готовность**: зарегистрировать расхождение и исправить код или изменить стандарт отдельным согласованным PR. Нельзя молча объявлять нереализованную политику действующей.

Изменять данный стандарт только в reviewable PR с причиной, влиянием на 15 доменов, безопасностью и тестами. Нет необходимости копировать полный текст во все доменные документы: они **ссылаются** на стандарт и фиксируют только специфические правила.

**Решение:** применять RM-PLATFORM-STANDARD-R2 как единую архитектурную базу дальнейшей разработки. Все неподтверждённые предметные выборы отмечены `DECISION REQUIRED`, а реальный production admission остаётся закрыт.

## 11. Нормативный контракт пользовательских сценариев R2

Этот раздел определяет **ожидаемое поведение продукта**, а не перечень уже готовых экранов. Каждый сценарий одновременно является входом для ТЗ доменного сервиса, отрицательных тестов, интеграционной приёмки и будущего интерфейса. **Не строить** отдельный workflow-engine, ACL-framework или новые API только потому, что сценарий документирован.

**Статусы:** **BASE** — существующее внутреннее ядро в `main` с ограничениями, а не готовый пользовательский E2E; **PR4** — историческая маркировка IAM-кандидата; после merge PR #4 считать его внутренним **BASE** (без HTTP/production); **TARGET** — утверждённый целевой пользовательский результат, разработка и приёмка ещё требуются; **DECISION REQUIRED** — бизнес-политика намеренно не утверждена и не должна «додумываться» в коде.

**Общий минимальный шаблон приёмки для каждого сценария:**
1. **Actor/tenant:** источник проверенной идентичности, выбранная организация, необходимые permissions и при необходимости ограничение конкретного объекта.
2. **Preconditions:** допустимые статусы объекта, входные данные, полнота связей и роль владельца агрегата.
3. **Success:** наблюдаемый результат, корректный следующий статус, что пользователь может прочитать после повторного входа.
4. **Failure:** отсутствие прав, чужой tenant, несуществующий/чужой object ID, неподходящий статус, неправильный payload, stale identity, конкурентная операция; **никаких частичных изменений**.
5. **Evidence:** кто/что/когда изменил, request/correlation ID где уместно, доменное событие и отсутствие PII/токенов в логах.
6. **Retry/recovery:** повтор команды, конфликт, отказ соединения/откат, а для внешнего уведомления — запрет дублировать бизнес-результат.
7. **Acceptance:** позитивный, негативный, cross-tenant и PostgreSQL concurrency тест для изменяющих операций; UI/HTTP E2E только после реального доверенного admission.

**Принцип статусов:** **BASE + TARGET** означает «часть операции реализована, но весь сценарий не принят»; **TARGET** не означает реализованный метод или зарегистрированное permission.

### 11.1 Персонажи и границы полномочий

| Участник | Намерение | Модель допуска |
|---|---|---|
| Владелец организации (OWNER) | Учредить/администрировать организацию, её участников и роли | Неделегируемая membership-возможность, без автоматического CRUD-владения всеми доменами |
| Администратор RM (PLATFORM_ADMIN) | Управлять глобальными аккаунтами/восстановлением | Отдельная глобальная политика, **нет** автоматического доступа к tenant PII/заказам |
| Руководитель продаж / менеджер | Клиенты, обращения, предложения, заказы | Настраиваемые роли и явные CRM/SALES permissions |
| Кладовщик | Приёмка, остатки, корректировка, выдача | Настраиваемые роли и явные INVENTORY permissions |
| Бухгалтер | Счета, оплаты, сверки | Будущие FINANCE permissions; не наследуются от SALES/INVENTORY |
| Маркетолог | Сегменты и разрешённые рассылки | Будущие MARKETING permissions + согласие получателя |
| Покупатель/гость | Ознакомление с витриной, заказ, проверка заказа | Публичный ограниченный контур и доказательство владения email/аккаунтом; не выдавать фиктивное членство в tenant |
| Системная задача | Доставка уведомлений, миграции, ключи, архив | Отдельная service identity/ограничения; не притворяться OWNER |

Названия должностей — **примеры назначаемых ролей**, не hardcoded Java-ролевая матрица. Проверять конкретный permission, а не текст должности.

## 12. Сквозные пользовательские сценарии: IAM и организация

### UC-IAM-01 — Вход, выбор и переключение организации [TARGET; auth-ядро BASE]

**Actor:** сотрудник нескольких организаций; **допуск:** валидный OIDC principal, ACTIVE account и ACTIVE membership выбранного ORGANIZATION workspace.

- **До:** пользователь существует и привязан к внешнему subject; права в разных tenant могут не совпадать.
- **Шаги:** (1) пройти доверенный login; (2) получить список **своих** доступных организаций без данных посторонних tenant; (3) выбрать организацию A; (4) выполнить разрешённое чтение; (5) переключиться на организацию B и получить отдельные роли/данные.
- **После:** сервер вычисляет права для B заново; в запросах/кэше/фильтрах данные A не сохраняются под видом B; отключённая организация не появляется как рабочая.
- **Отказы:** отсутствующее членство, PENDING/SUSPENDED/DELETED account, SUSPENDED/CLOSED workspace, expired/forged token, подмена tenantId или actorId → DENY до предметного чтения.
- **Приёмка:** один user в A и B с различными grants; переход A→B→A; отсутствие утечки в списках/поиске/заголовках; реальный OIDC/BFF ещё **не готов**.

### UC-IAM-02 — Первичная организация и доступ владельца [TARGET]

**Actor:** новый верифицированный владелец; **действие:** создать организацию, workspace и первоначальное OWNER membership.

- **До:** данные организации проверены, дубликаты/повтор регистрации имеют понятное правило; пользователь идентифицирован.
- **Шаги:** зарегистрировать организацию → создать связанный workspace → записать единственного или нескольких OWNER → активировать по утверждённой процедуре → создать первую функциональную роль и назначить доступ сотруднику.
- **После:** все ссылки organization/workspace/member согласованы, tenantId уникален; повтор запроса не создаёт второй workspace/OWNER; OWNER может управлять RBAC без неявного доступа ко всем операциям.
- **Отказы:** неполные реквизиты, одинаковый регистрационный ключ, отсутствие реального подтверждения владельца, частичная ошибка транзакции → rollback либо документированное PROVISIONING.
- **Приёмка:** успешный и повторный bootstrap, rollback, межтенантская изоляция; реальные юридические/identity критерии подтверждения — **DECISION REQUIRED**.

### UC-IAM-03 — Приглашение, активация и уход сотрудника [TARGET]

**Actor:** уполномоченный администратор членства; **допуск:** отдельная административная политика; до её утверждения не заменять её универсальным CRM_WRITE.

- **Шаги:** указать существующего/нового global user → создать INVITED membership **в конкретную организацию** → подтвердить приглашение доверенным каналом → ACTIVE → назначить разрешённые роли → при уходе перевести в SUSPENDED/LEFT.
- **После:** история статусов сохранена; роли и права не переходят в другой tenant; LEFT не может читать старые клиентские карточки. Повтор приглашения не должен создавать дубликат пары organization/user.
- **Отказы:** чужой tenant, подмена subject, недействительное/истёкшее приглашение, попытка самому себе назначить admin, потеря последнего OWNER.
- **Приёмка:** приглашение, отказ, повтор, активация, отзыв, блокировка конкурентной команды; внешние приглашения и передача владения пока **не реализованы**.

### UC-IAM-04 — Назначение функциональных ролей [BASE; workflow TARGET]

**Actor:** активный OWNER; **permission:** TENANT_RBAC_MANAGE (неделегируемый).

- **До:** target member ACTIVE в том же tenant; разрешение зарегистрировано в DomainPermission; functional role принадлежит тому же tenant.
- **Шаги:** создать роль по произвольному бизнес-названию → выдать один/несколько grants → назначить сотрудникам → убедиться, что хотя бы один действующий сотрудник имеет рабочий grant → включить enforcement → проверить effective permissions.
- **После:** роли tenant-local; несколько ролей объединяются, но не дают wildcard; OWNER не получает бизнес-права автоматически; изменения записаны в неизменяемую историю.
- **Отказы:** назначение себе, grant TENANT_RBAC_MANAGE, outsider, чужая роль, несуществующий permission, пустая конфигурация, duplicate grant; повтор создания одной и той же роли по code не создаёт дубликат.
- **Приёмка:** role/permission/assignment isolation, включение, revoke, disable/enable роли, audit; существующие сервисы BASE, пользовательский UI — TARGET.

### UC-IAM-05 — Блокировка, отзыв прав и восстановление [BASE role revoke + lifecycle; TARGET recovery]

**Actor:** OWNER для доступа к своей организации; PLATFORM_ADMIN для глобального аккаунта.

- **Шаги:** отозвать grant/роль **либо** приостановить membership/tenant/account → открыть новую команду → проверить DENY → восстановить статус только в разрешённом административном пути → повторно вычислить текущие permissions.
- **После:** уже допущенная транзакция и транзакция отзыва сериализованы в PostgreSQL; после commit отзыва новая команда не проходит; события отзыва/восстановления неизменяемы.
- **Отказы:** одновременный revoke/command, stale JPA entity, восстановление учётной записи без полномочия, самоблокировка владельца, блокировка последнего OWNER/администратора, попытка доступа к SUSPENDED tenant.
- **Приёмка:** обе очередности двух реальных PG-транзакций, rollback-on-deny, account/member/tenant и назначенные роли; расширенный внутренний код реализован в **merged PR #4**, однако независимый production sign-off отсутствует. Transfer ownership, emergency recovery и законная деактивация администраторов — **DECISION REQUIRED**, не импровизировать.

### UC-ORG-01 — Создание и поиск бизнес-локации [BASE; lifecycle TARGET]

**Actor:** сотрудник с ORGANIZATION_LOCATION_WRITE для создания, ORGANIZATION_LOCATION_READ для просмотра.

- **Приёмка:** correction после активных резервов, параллельная выдача/приход, rollback, immutable movement. Процесс инвентаризации/акт списания и approval — **TARGET**.

### UC-INV-04 — Поиск остатков и настройки склада [BASE read/settings; UX TARGET]

**Actor:** INVENTORY_STOCK_READ для просмотра; INVENTORY_SETTINGS_MANAGE для изменения политики отбора/параметров.

- **Шаги:** выбрать tenant и склад → найти SKU с фильтрами → увидеть on_hand/reserved/available → просмотреть страницы с устойчивой сортировкой → отдельно изменить разрешённую политику picking, если есть permission.
- **После:** ни одна строка другого tenant не видна; размер страницы 1..100, отрицательный page — ошибка; настройки меняются транзакционно с аудитом по контракту домена.
- **Отказы:** другой tenant, прямой запрос чужой позиции, отменённая роль, конкурентное изменение policy.
- **Приёмка:** two-tenant pagination/search, вычисление available, запрет записи с одним read permission, запрет считать COUNT+PAGE единым отчётным snapshot. Утверждение стоимостной методики требует отдельной финансовой политики, не только права настройки.

## 16. Sales — полный путь продавца и склада

### UC-SALES-01 — Получить и проверить новый заказ [BASE read/internal checkout; dashboard TARGET]

**Actor:** сотрудник с SALES_ORDER_READ; **до:** заказ PLACED создан продавцу через допустимый канал.

- **Шаги:** выбрать tenant → открыть список со статусом/датой → выбрать заказ и его строки → проверить seller tenant, offer/SKU, количество и зафиксированную цену до принятия решения.
- **После:** чтение не изменяет статус/резервы; покупательские персональные данные не раскрываются без отдельного PII policy; страницы ограничены.
- **Отказы:** чужой orderId, чужой tenant, отсутствие permission, попытка получить детальную PII из DTO списка.
- **Приёмка:** фильтр status/time, стабильный page, no cross-tenant leakage; полноценное read-detail/операторский экран — **TARGET**.

### UC-SALES-02 — Подтвердить заказ и зарезервировать товар [BASE internal; UX TARGET]

**Actor:** сотрудник, имеющий **одновременно** SALES_ORDER_CONFIRM и INVENTORY_RESERVE.

- **До:** заказ PLACED у своего seller tenant, непустые строки, offer корректно разрешён в SKU, доступный остаток покрывает каждую полную строку, один склад для всего заказа в R2.
- **Шаги:** выбрать warehouse → вызвать команду подтверждения → lock order → проверить пару транзакционных permissions → упорядочить строки по SKU → создать по одному полному ACTIVE резерву на строку → записать CONFIRMED и историю одной транзакцией.
- **После:** заказ CONFIRMED только если **все** резервы созданы; reserved увеличен точно на суммарные количества; повтор с тем же warehouse возвращает устойчивый результат без второго резерва.
- **Отказы:** недостача одной строки, чужой склад, разный warehouse на retry, отсутствует одно из permissions, concurrent подтверждения, чужой orderId → целиком rollback, не оставлять «половину заказа».
- **Приёмка:** 2 транзакции, 2 competing orders за SKU, полный/неполный stock, cross-tenant, неизменяемая история; split warehouse и частичный резерв **не включены** в R2.

### UC-SALES-03 — Отменить заказ и снять резерв [BASE internal; UX TARGET]

**Actor:** сотрудник с SALES_ORDER_CANCEL + INVENTORY_RELEASE.

- **Шаги:** открыть допустимый незавершённый заказ → проверить статус и ранее отгруженные резервы → перевести в CANCELLED и освободить все ACTIVE резервы одной транзакцией → открыть историю.
- **После:** CANCELLED не имеет ACTIVE резервов, reserved уменьшен на освободившиеся количества, on_hand не уменьшается; повтор CANCELLED — безопасный no-op при согласованном состоянии.
- **Отказы:** COMPLETED, OUT_FOR_DELIVERY, READY_FOR_PICKUP, REJECTED или уже FULFILLED резерв; missing permission, чужой заказ, конфликт при отмене/выдаче.
- **Приёмка:** reserve→cancel, retry, одновременно cancel/fulfill, отсутствие утечки товарных данных другого tenant.

### UC-SALES-04 — Выдать товар и завершить внутреннее исполнение [BASE internal; UX TARGET]

**Actor:** сотрудник с SALES_ORDER_FULFILL + INVENTORY_FULFILL.

- **До:** заказ CONFIRMED или PREPARING, каждый item line покрыт ACTIVE reservation.
- **Шаги:** открыть подтверждённый заказ → проверить полный резерв → провести выдачу/списание по каждому резерву → вставить по одному неизменяемому fulfillment movement → перевести заказ в COMPLETED.
- **После:** каждый резерв FULFILLED, reserved уменьшен, on_hand уменьшен на то же количество; повтор COMPLETED не создаёт движение заново.
- **Отказы:** неполные резервы, недоступные статусы, уже освобождённый резерв, параллельная отмена, чужой tenant, один из парных permissions отсутствует.
- **Приёмка:** exactly-once debit, два параллельных fulfill, инвариант остатка, history, rollback. **COMPLETED = завершение внутреннего stock-исполнения, не юридически подтверждённая доставка и не оплата.**

### UC-SALES-05 — Отгрузка, доставка, возврат и рекламация [TARGET; separate contracts]

**Actor:** менеджер, склад, покупатель; **действия:** только после утверждения статусов и полномочий.

- **Целевой путь:** подготовить заказ → упаковать/передать → зафиксировать подтверждение передачи/получения → провести возврат либо рекламацию отдельными корректирующими событиями.
- **После:** доставка и физическая выдача имеют собственные доказательства; возврат не переписывает исходное списание и заказ.
- **Отказы:** выдача без резерва, двойное списание, некорректный возврат после отмены, подмена получателя/склада.
- **Приёмка:** order/stock/shipment reconciliation. Статусы доставки, частичные отгрузки, сроки и возвратные документы — **DECISION REQUIRED** до кода.

## 18. Матрица отрицательных испытаний — обязательна для сценариев выше

| Класс | Проверка | Обязательный результат |
|---|---|---|
| Identity | Неизвестный, SUSPENDED, истёкший или подложный субъект | DENY без business SQL mutation/PII |
| Tenant | user A + tenant B, смешанный join, чужой file/order/SKU ID | Нет результата, side effects и раскрытия существования чужого объекта |
| RBAC | Нет одного из парных permissions, role disabled, grant revoked | DENY, откат всех изменений |
| Object scope | Нет назначения на клиента/склад, если политика утверждена | DENY до мутации/PII; не выдумывать объектные ACL заранее |
| Validation | Null ID, неправильная валютa/точность, отрицательный stock, нет KATO, нет consent | Validation error и неизменная БД |
| State transition | Повтор terminal, неправильный источник перехода, попытка cancel fulfilled | Идемпотентный документированный replay либо отказ без побочных эффектов |
| Concurrency | Два конкурирующих заказа за SKU; revoke vs command; одновременный duplicate requestKey | Нет oversell, потерянного отзыва, двойного движения или события |
| Failure recovery | Ошибка во второй половине транзакции, недоступная БД, ошибка доставки email | Transaction rollback, безопасный retry; external retry не дублирует заказ |
| Data protection | Нет CRM_PII_READ, прямая ссылка на вложение, открытый audit/log | Нет расшифрованных PII, токенов и ключей |
| Performance/operations | Много записей, paging, переход с заполненной PG, восстановление | Измеримые p95/p99, проверенная миграция, audit reconciliation, backup restore |

**Для тестов:** пользоваться синтетически заполненной PostgreSQL с минимум двумя tenant, несколькими владельцами, сотрудниками, складами и заказами; отдельные соединения для гонок. Успех чистой базы не заменяет populated-upgrade/recovery evidence. Полный проектный E2E требует реального OIDC/HTTP и отдельных release gates.

## 20. Заключение сценарного ревью и приоритет реализации

**Проверено по исходникам main на 2026-11-21:** `TenantRoleService`, `TenantAuthorization`, `CrmCustomerService`, `AutoOrderService`, `SalesInventoryCommandService`, `InventoryAuthorizedCommandService`, `StockBalanceQueryService`, `OrganizationLocationService`, `DomainPermission`. Положительные возможности помечены BASE **только** при наличии соответствующего internal Java сервиса. Утверждение документа не изменяет deployed runtime.

**Выявленные расхождения, требующие отдельной разработки, а не документального переименования:**
- IAM member/account/tenant status, transactional revoke и stale JPA admission включены из PR #4 в `main`; реальные HTTP/OIDC/BFF и независимое security approval остаются HOLD.
- CRM потребует явной политики read-after-create PII и ответственностей/воронки; contact consent в `main` использует общий CRM_WRITE, а не специально согласованный CONSENT permission.
- Catalog publish/price management, полноценная пользовательская карточка заказа, складская нулевая инициализация и подробная история движения не считаются принятыми E2E.
- Реальный OIDC/BFF/public checkout email, абонентские лимиты, платежи, доставка и междоменные уведомления — отдельные вертикали и production HOLD.

**Последовательность:** внутреннее IAM ядро merged, production security gate HOLD → R2.1 Inventory → R2.2 Sales → R2.3 CRM → доверенные adapters/покупательский E2E → остальные домены по приоритету. Переход между этапами — только с тестами user journey, отрицательными сценариями и доказательством инвариантов.

**Нормативное правило:** если сценарий записан здесь, но сервис или тест отсутствует, его статус — TARGET, а не готовая функция. Для каждого реализуемого UC планировать только нужные методы, миграции и тесты, без дополнительного архитектурного слоя.

## 21. Минимальный DTO-стандарт RM-R2

**Цель:** единообразные границы данных между будущим HTTP/BFF, прикладными сервисами и UI без дублирования доменной модели и инфраструктурных обёрток. Это **контракт на следующую реализацию**, а не требование переписывать все существующие Java records или открывать REST-контроллеры сейчас.

### 21.1 Четыре вида DTO, не больше

| Назначение | Имя | Пример | Правило |
|---|---|---|---|
| Изменяющая команда | `*Request` | `ReceiveStockRequest`, `ConfirmOrderRequest` | Только поля, которые вправе выбирать пользователь; **без `actorId` / `tenantId` / роли** |
| Результат команды | `*Response` либо `*Result` внутри Java | `StockMovementResponse`, `OrderCommandResult` | ID, подтверждённый статус и фактически сохранённые значения; не возвращать JPA Entity |
| Чтение / карточка | `*Dto` | существующие `LocationDto`, `StockBalanceDto`, `SalesOrderDto` | Только необходимые поля по конкретному permission и правилам PII |
| Фильтр списка | `*Search` | `LocationSearch`, `StockSearch`, `SalesOrderSearch` | Неизменяемые, ограниченные фильтры; null означает «фильтр отсутствует», если иное явно не оговорено |

Не создавать классы `BaseRequest/BaseResponse`, DTO inheritance, `Map<String,Object>` для бизнес-состояний, универсальный CRUD service или собственный serialization engine. **Один DTO на один осмысленный контракт**, а не один DTO на каждую таблицу. Для внутренних сервисов допустимы небольшие локальные `record`/value object без суффикса DTO.

### 21.2 Стиль Java и владение контрактами

- По умолчанию **Java 21 `record`** для immutable request/response/search; `class` только при реальной необходимости. DTO не является `@Entity`, не содержит `JdbcTemplate`, lazy relation, SQL/crypto ключей или бизнес-транзакций.
- Размещать в `kz.rm.<domain>.dto`; общую инфраструктуру заводить **только при двух фактически одинаковых контрактах**. Домены не импортируют DTO других доменов как свою persistence-модель; взаимодействие — через узкие application contracts.
- Называть поля `camelCase` в Java/JSON, ID — `UUID`, количество/суммы — `BigDecimal` (не `double`/`float`), деньги — `amount + currency` с проверкой валюты; дата-время события — `Instant` (ISO-8601 UTC), календарная дата без времени — `LocalDate`.
- Запрещено произвольно переводить `BigDecimal` в `double`, округлять суммы на уровне DTO или смешивать количество и стоимость. Денежное округление и единица количества принадлежат доменной методике.
- Внешний DTO должен быть **независим от JPA Entity и enum сущности**, если публичная схема иначе станет зависеть от persistence. Внутренние существующие `LocationDto` и поисковые фильтры могут пока использовать entity enum — это **legacy internal**, а не окончательная публичная схема.
- Простое отображение JDBC → record делается конструктором; MapStruct применять выборочно для повторяемого entity→DTO отображения (как существующий `LocationMapper`). Не добавлять обязательный mapper-слой ради двух полей.

### 21.3 Доверенная идентичность и безопасность ответа

- `actorId`, `userId` вызывающего и права **не принимаются из клиентского тела/фильтра**. Verified principal приходит только из доверенного IAM adapter. `tenantId` может быть идентификатором выбранного workspace в маршруте/context, но на сервере заново проверяется активное членство; он **не** становится доверенным лишь потому, что передан клиентом.
- `locationId`, `itemId`, `customerId`, `orderId` из запроса — **ссылки на объекты, не доказательство доступа**. Домен подтверждает tenant ownership, object scope и статус перед чтением/изменением.
- В ответах: минимум необходимых полей, **без токенов, JWT, ключей, шифроконтейнеров, внутренних хэшей, персональных данных по умолчанию и stack trace**. Права `CRM_WRITE` **не подразумевают** `CRM_PII_READ`; ответ createPerson/addContact должен отдельно пройти PII response policy до публичного API.
- Роли, grants и effective permissions из IAM выдаются только в разрешённой области tenant. OWNER не получает скрыто доступ к клиентским PII.
- `tenantId` допустим во **внутренних** результатах и для трассируемости, например существующем `StockBalanceDto`; в публичных ответах передавать его **только по реальной потребности**, не как способ расширить доступ.

### 21.4 Валидация и контракт полей

- На будущей границе HTTP: `jakarta.validation` (`@NotNull`, `@NotBlank`, `@Size`, `@DecimalMin` и т.п.) для формата/простого диапазона; **сервис повторно** проверяет существенные инварианты и разрешения. Валидация DTO не заменяет транзакцию, FK, check constraint и RBAC.
- Trim, case normalization, email normalization выполняются по явно определённым правилам **в одном месте**; не изменять произвольно имя клиента. Неизвестное enum/status и неверный тип/UUID — ошибка, а не молчаливый default.
- `null` и отсутствие необязательного поля эквивалентны **только** там, где так определяет контракт, например search filters. В командах **не интерпретировать `null` как «обнулить» без явного правила**. Использовать отдельные команды для существенных изменений статусов; generic PATCH пока не нужен.
- Для изменяемых карточек, где это нужно, включать `rowVersion` в response и `expectedVersion` в update request; устаревшая версия → конфликт без перезаписи. Для складских остатков применять уже существующую транзакционную модель блокировок, не навязывать optimistic locking поверх неё.
- Корректное `createdAt/updatedAt` задаётся сервером. **Не принимать** из клиентского request `createdAt`, `status` существующего заказа, `unitPriceSnapshot`, `reserved`, `onHand` как авторитетное состояние.

### 21.5 Пагинация и ошибки: использовать штатный Spring

- Существующие внутренние списки возвращают `Page<T>`/DTO с **page ≥ 0, 1 ≤ size ≤ 100**, стабильной сортировкой и обязательным `tenant_id` в SQL/JPA predicate. Не переписывать их без необходимости.
- Для будущего стабильного публичного API, **не сериализовать JPA Entity или внутренний `PageImpl` как официальный контракт**. Достаточно простого `PageResponse<T>(items,page,size,totalElements)`; реализация только при появлении HTTP adapter. COUNT и PAGE не гарантируют единый snapshot при конкурентной записи.
- Для HTTP-ошибок использовать **Spring `ProblemDetail` (RFC 9457)**, а не новый `ErrorDto` и не персональные exception messages. Минимум: `status`, `title`, безопасный `detail`, стабильный `code` extension и `traceId` при наличии трассировки.
- Соглашение API после появления транспорта: **400** — неверный ввод, **401** — не аутентифицирован, **403** — нет права, **404** — объект отсутствует **или недоступен без раскрытия его существования**, **409** — недопустимый переход/конфликт версии или idempotency key, **5xx** — инфраструктурная ошибка. Не сообщать чужие `tenantId`/PII в `detail`.
- Retry-sensitive mutating API получает один `Idempotency-Key` (HTTP header в будущем; во внутренних командах — `String idempotencyKey`). Повтор с тем же каноническим payload возвращает прежний результат; иное тело с тем же ключом — 409 без побочных эффектов. Не вводить общий распределённый idempotency сервис.

### 21.6 Минимальные образцы (TARGET, не утверждение существующих REST endpoints)

```java
// INVENTORY: request body contains only business input.
// Tenant and actor are resolved in a trusted adapter, never from this record.
public record ReceiveStockRequest(
        @NotNull UUID locationId,
        @NotNull UUID itemId,
        @NotNull @DecimalMin(value = "0.0", inclusive = false) BigDecimal quantity
) {}

// SALES: orderId is a validated route identifier; body only selects location.
public record ConfirmOrderRequest(@NotNull UUID locationId) {}

// CRM: do not return a fullName to a caller lacking CRM_PII_READ.
public record CustomerSummaryDto(UUID id, String type, String displayName) {}

// Only when a public API exists: a stable, minimal list projection.
public record PageResponse<T>(List<T> items, int page, int size, long totalElements) {}
```

Это **иллюстрации контракта**, не предложение добавить четыре `record` сейчас и не замена доменным результатам уже реализованных сервисов. Реальный response проектируется по действующему permission и предметным полям. Для CRM при отсутствии `CRM_PII_READ` поле `displayName` физлица должно отсутствовать/быть безопасно замаскировано согласно утверждённой политике; **нельзя передавать plaintext и рассчитывать на скрытие на UI**.

### 21.7 Сверка с существующими DTO в main

| Уже существует | Фактический контракт | Что не следует обещать без следующего этапа |

### 22.1 Критерии приёмки DTO-стандарта

1. **Никакой JPA Entity в публичном request/response**; существующие internal DTO не переписывать автоматически.
2. При подмене user/tenant/object ID — отказ без изменения БД/утечки. **Не принимать** `actorId` из пользовательских данных.
3. `CRM_WRITE` без `CRM_PII_READ`: ни create/read/contact response, ни error не раскрывают закрытые поля. Проверять **не только GET, но и ответ мутации**.
4. `BigDecimal` проходит round-trip без потери точности; количества и денежные суммы не смешиваются.
5. Неизвестный статус, некорректный диапазон/страница, пустое имя, чужой ID и конфликт версии имеют предсказуемую ошибку без SQL side effect.
6. `Page` стабилен по порядку и tenant-filter; **не утверждать** консистентность COUNT и PAGE без snapshot.
7. Повторение mutating request с тем же idempotency key соблюдает фактический доменный контракт; другой payload не меняет ledger/order вторично.
8. При появлении публичного адаптера — сериализационные/контрактные тесты для camelCase, `Instant`, `BigDecimal`, ошибочного payload, отсутствующих полей и sanitized ProblemDetail; **до появления адаптера не создавать фиктивные web-layer тесты**.

### 22.2 Границы текущего изменения

**Только стандарт и ТЗ**: `DomainPermission`, сервисы, существующие `LocationDto`/`StockBalanceDto`/`SalesOrderDto`, SQL, Liquibase и API не менять. Пакеты существующих DTO считать базой. Новые DTO создавать **внутри соответствующей функциональной вертикали R2.1/R2.2/R2.3** с её тестами и только если публичный или межсервисный контракт действительно в них нуждается.

**Открытые решения неизменны:** D-01..D-10 в §19; DTO не должен молча принять вместо них бизнес-политику.


**Git workflow (2026-11-21):** `main` — проверенная интеграционная ветка; `base_dev` — единственная постоянная ветка разработки. H2 и PostgreSQL запускаются на push в обе ветки и на PR. Допуск изменений в `main` — по PR с review и точным CI. Архивные ветки не считаются активной разработкой.

## 23. IAM — внутренний процесс входа и раздачи ролей (service-only R2.3)

**Решение:** один процесс аутентификации для каждого человека (покупатель, сотрудник, владелец организации, администратор RM); полномочия определяются **после** проверки identity. Не делать разные логины или отдельные аккаунты по типам пользователя. Не создавать контроллеры до подтверждения доверенного HTTP/OIDC admission.

**Целевой процесс и текущая реализация в `base_dev` (до merge — кандидат):**

| Шаг | Кто действует | Внутренний сервис | Проверки и последствия |
|---|---|---|---|
| A. Identity | Любой человек | `OidcActorResolver` → `VerifiedActor` | Только подтверждённый subject, ACTIVE account и действующий токен; настоящий HTTP/BFF пока HOLD |
| A2. Email proof | Любой новый/сменяющий адрес пользователь | Существующий `EmailIdentityService` + проектируемый R2.5 email-change flow | При первой регистрации `emailVerified=false`; при смене новое значение требует **нового** подтверждения, старое CURRENT до успешного proof; см. §25 |
| A1. Свои контексты | Любой вошедший пользователь | `MyAccessService.myTenants/myGlobalRoles/myFunctionalRoles` | Список только ACTIVE организаций текущего пользователя; глобальные роли отдельно; функциональные роли только своего tenant |
| B. Назначить владельца новой компании | Глобальный `PLATFORM_ADMIN` | `PlatformTenantBootstrapService.provision` | ACTIVE admin, ACTIVE существующий user, создать organization/workspace/OWNER atomically; global admin **не получает** бизнес-прав |
| C. Изолировать новую организацию | Система | шаг B | `iam_tenant_rbac_config.enforced=TRUE` немедленно; **default deny** любых бизнес-прав до конкретного назначения |
| D. Пригласить сотрудника | Активный OWNER организации | `TenantMemberEnrollmentService.invite` | Только существующий ACTIVE global account; INVITED membership в одном tenant, без прав; один invite event |
| E. Принять приглашение | Сам приглашённый сотрудник | `TenantMemberEnrollmentService.accept` | `VerifiedActor.userId` точно совпадает с адресатом; ACTIVE workspace, enforced RBAC; переход INVITED→ACTIVE, единичный audit |
| F. Создать функциональную роль | OWNER | `VerifiedTenantRoleCommands.createRole/grant` | Tenant-owned роль, разрешения только из `DomainPermission`, `TENANT_RBAC_MANAGE` не делегировать |
| G. Назначить роль сотруднику | OWNER | `VerifiedTenantRoleCommands.assign` | Сотрудник ACTIVE в том же tenant, роль ACTIVE; ни одного бизнес-permission до успешного назначения |
| H. Работать в CRM/SALES/INVENTORY | Сотрудник | `TenantAuthorization.require/requireForCommand` | ACTIVE user+workspace+membership, актуальная роль и конкретное permission; дополнительно объектная политика домена |
| I. Уволить, отозвать доступ | OWNER / PLATFORM_ADMIN по своей области | `TenantAccessStatusService`, `GlobalAccountStatusService` | Tenant suspension не равно global suspension; отзыв сериализован с командами, права не переходят в другой tenant |

**Граница доверия:** платформа не принимает `actorId` из body/DTO. Global `PLATFORM_ADMIN` может создать организацию с первым OWNER; это **не универсальный администратор CRM**. OWNER создаёт произвольно названные функциональные роли и назначает их сотрудникам; не получает автоматически все права продаж, склада или PII.

**Статусы и повтор:** повтор `provision` с тем же tenant UUID и тем же владельцем/реквизитами возвращает созданную пару; другой payload с тем же tenant UUID отклоняется. Повтор `invite` для INVITED и `accept` для ACTIVE — no-op без повторного audit. При потере ACTIVE account, блокировке workspace, неправильной роли, попытке самоприглашения или обращении к чужой организации — DENY. Новая организация по умолчанию **строже**, чем старый tenant в compatibility mode: `enforced=TRUE` с момента создания.

**Граница §23 после внутреннего IAM-R2.4:** первичное доверенное назначение `PLATFORM_ADMIN`, выдача/отзыв глобального admin, подтверждённая передача `OWNER` и аварийное восстановление описаны в §24 и реализуются сервисами в `base_dev` (кандидат до merge). По-прежнему нет создания глобального пользователя из произвольного email, SMTP-приглашений, HTTP/BFF/OIDC-провайдера, подтверждения владения юридическим лицом, миграции заполненной БД, восстановления без действующего сотрудника и независимого security approval.

### 23.1 Критерии процессной квалификации (без контроллеров)

1. Platform admin → organization/tenant/OWNER; replay без второго tenant и audit; чужой пользователь не может provision.
2. OWNER → role → grant → invite staff; до активации нельзя назначить роль; до назначения роль не даёт доступ.
3. Сотрудник принимает приглашение **своим** verified principal; active membership сам по себе не обходит enforced RBAC.
4. Один сотрудник в двух tenant видит обе свои организации, но роль SALES одного tenant не действует в другом; гость без membership не видит организации. Suspended account немедленно теряет доступ к чтению даже со старым VerifiedActor.
5. OWNER назначает рабочее permission; сотрудник получает только его и не может назначать себе/другим права.
6. Platform admin не читает CRM другого tenant, даже если создал организацию. Сотрудник А не получает роль/данные организации B.
7. Два параллельных принятия приглашения → одна активация, один MEMBER_JOINED event; повторная команда идемпотентна.
8. Suspended/LEFT membership, suspended account и tenant запрещают операции; отзыв доступа не допускает race с новой изменяющей командой.
9. Синтетический `VerifiedActor`/OIDC resolver и реальные PostgreSQL/H2 service tests достаточны **только для внутренней квалификации**. Реальные токены, пользовательский HTTP/BFF, SMTP/invite, security/least-privilege и production load — отдельные gates.

**Ограничение архитектуры:** не строить универсальный workflow/ABAC, не создавать controller и формы входа пока этот service-only сценарий не пройдёт PostgreSQL и H2 на точном SHA. Новые таблицы допустимы только при реальной необходимости; текущий шаг использует существующую IAM-схему и добавляет только значения событий аудита Liquibase `0037`.

## 24. IAM — первичный администратор, двухсторонняя передача OWNER и emergency recovery

**Рубеж RM-IAM-R2.4:** сервисы + PostgreSQL/H2 процессные тесты. **Кандидат в `base_dev`**, до merge не является готовностью `main`; без HTTP-контроллеров, пользовательского UI, отдельного RBAC-движка и автоматических системных ролей. Основной стандарт §4–§5 остаётся без изменений.

### 24.1 Доверенная первичная выдача PLATFORM_ADMIN (GOV-01)

**Участник:** оператор развёртывания с заранее выданным случайным одноразовым секретом длиной от 32 символов; получатель — уже существующий **ACTIVE OIDC-linked** RM account, представленный `VerifiedActor`.

1. Bootstrapping **выключен по умолчанию** (`RM_IAM_BOOTSTRAP_ENABLED=false`). Оператор временно разрешает его из доверенного окружения, передавая **SHA-256 hex** bootstrap-секрета через `RM_IAM_BOOTSTRAP_TOKEN_SHA256`, а сам секрет — исключительно во внутреннюю команду `PlatformAdminGovernanceService.bootstrapFirstAdmin`. Не хранить открытый секрет в application.yml, Git, DB, журнале или параметрах HTTP; приложение не получает встроенный пароль администратора.
2. Сервис сравнивает digest в постоянном времени и **в одной транзакции** блокирует аккаунт кандидата и singleton `iam_global_admin_guard`. Отказывает, если секрет/конфигурация неверны, аккаунт неактивен/не связан с OIDC, guard уже использован **или когда-либо существовал** `PLATFORM_ADMIN`.
3. Один первый `PLATFORM_ADMIN` появляется в `iam_global_role_assignment`, guard становится необратимо `bootstrapped=TRUE`, событие `ADMIN_BOOTSTRAPPED` добавляется в append-only `iam_global_role_event`. Повтор — DENY, не новый администратор.
4. Для обновления ранее существовавшей установки Liquibase `0042` закрывает bootstrap по наличию исторической роли `PLATFORM_ADMIN` (в том числе отозванной). При потере **всех** глобальных администраторов нельзя повторно открыть bootstrap; это отдельная offline disaster-recovery процедура с внешней проверкой личности.

**Владелец полномочий:** `PLATFORM_ADMIN` не получает автоматически `CRM_READ`, `CRM_PII_READ`, `INVENTORY_*` и права OWNER в любой компании. Его полномочия — только узкие глобальные IAM-операции.

### 24.2 Выдача и отзыв глобального администратора (GOV-02)

**Участник:** существующий `PLATFORM_ADMIN` с ACTIVE account.

- `grantAdmin(actor,targetUserId)`: target ACTIVE и OIDC-linked; повтор не создаёт второй active grant, отзывное назначение повторно активируется с новым событием. Аудит `ADMIN_GRANTED`.
- `revokeAdmin(actor,targetUserId)`: защита от self-revoke и потери последнего действующего администратора; аудит `ADMIN_REVOKED`. Не изменяет членство в организациях. Любой account suspension глобального администратора возможен только после отдельного отзыва его global role.
- Глобальные изменения сериализованы блокировкой `iam_global_admin_guard`. Роли организаций из `iam_tenant_role` от этого не меняются.

**Граница безопасности:** исходный актор всегда `VerifiedActor` с проверкой ACTIVE-статуса в DB, а не UUID, предоставленный клиентом. Привилегии оцениваются по текущему DB-гранту, не по старому JWT claim или кэшу.

### 24.3 Передача владельца организации (OWN-01)

**Участники:** действующий **OWNER** и его выбранный преемник, имеющий ACTIVE OIDC-linked account и ACTIVE membership именно в этом tenant.

1. OWNER вызывает `TenantOwnershipTransferService.requestTransfer(owner,tenantId,successorId)`. Проверяются активность владельца, tenant и преемника. Сохраняется один запрос `PENDING` на tenant с `requestId` и сроком действия **24 часа**; повтор той же команды возвращает тот же запрос. Параллельный другой запрос запрещён.
2. Преемник **собственным `VerifiedActor`** вызывает `acceptTransfer(successor,tenantId,requestId)`. Проверяются точный адресат, актуальность, срок, статус членов и собственное согласие преемника, а не согласие старого OWNER за него.
3. **Одна транзакция:** преемник получает неделегируемую membership-роль `OWNER`; предыдущий владелец переводится в `MEMBER`; запрос `ACCEPTED`; событие `OWNER_TRANSFER_ACCEPTED`. При любом отказе весь переход откатывается. До принятия первый OWNER сохраняет право управления.
4. `cancelTransfer` до принятия доступен только инициатору; записи остаются в `iam_tenant_rbac_event`. Истёкший, отменённый, чужой или поддельный запрос — DENY. Повтор принятого запроса идемпотентен до создания следующего запроса.

**Правило:** перевод `OWNER` не копирует функциональные grants и не выдаёт права просмотра PII или складских операций. Наличие нескольких владельцев в другой организации никак не влияет на данную.

### 24.4 Аварийное восстановление (OWN-02)

**Участник:** проверенный `PLATFORM_ADMIN` с документированным incident/ticket ID (`incidentCode` формата `[A-Z0-9_-]{6,80}`). **Строгий допуск:** в целевой организации **нет ни одного действующего OWNER** (одновременно ACTIVE membership + ACTIVE global account).

- `PlatformTenantRecoveryService.recoverOwner(admin,tenantId,targetUserId,incidentCode)` доступен только для ORGANIZATION workspace в состоянии ACTIVE или SUSPENDED, и только если кандидат — **уже существующий ACTIVE участник данного tenant** с OIDC-linked account, **не OWNER и не сам инициирующий PLATFORM_ADMIN**. Стороннего человека он присоединить не может.
- Под блокировкой глобальной роли, учётной записи кандидата и workspace транзакция демотирует прежние неработоспособные OWNER в MEMBER, делает кандидата OWNER, аннулирует ожидающий перевод **с отдельным аудируемым событием отмены** и фиксирует `OWNER_DEMOTED_BY_RECOVERY` / `OWNER_RECOVERED`. Это гарантирует, что восстановление старого аккаунта не вернёт ему право OWNER автоматически.
- Если workspace SUSPENDED, новый владелец восстанавливает его **отдельной** командой `TenantAccessStatusService.restoreTenant`. Восстановление не превращает PLATFORM_ADMIN в сотрудника, владельца либо получателя клиентских данных.
- Если хотя бы один владелец всё ещё активен, либо нет действующего сотрудника, сервис отказывает: первый случай требует обычной передачи OWN-01, второй — отдельного offline emergency-runbook (пока HOLD).

**Не открывать production:** даже после H2/PG service GREEN остаются независимый security-review, реальный trusted issuer/OIDC/BFF, физическое хранение и доставка operator bootstrap secret, least-privilege DB, populated-upgrade/recovery и подготовленный offline recovery runbook.

## 25. IAM-PII-R2.5 — глобальное шифрование профиля и подтверждение email

**Статус:** R2.5A и R2.5B — внутренние сервисы + H2/PostgreSQL испытания в `base_dev` (до merge кандидаты); R2.5C — encrypted profile service + opt-in offline migration, с отдельным обязательным populated-PostgreSQL cutover gate. **Полная R2.5 НЕ production-ready.** Нормативные требования этого раздела обязательны для последующих IAM-вертикалей. Подробный процессный и миграционный контракт — [RM-IAM-PII-R2.5-GLOBAL-PROFILE-EMAIL-VERIFICATION](../spec/RM-IAM-PII-R2.5-GLOBAL-PROFILE-EMAIL-VERIFICATION.md). **Никаких контроллеров до квалификации сервисов.**

### 25.1 Принятые продуктовые инварианты

1. **Первая регистрация:** `emailVerified=false` без исключений. Не считать наличие email либо `email_verified` claim из внешнего OIDC доказательством RM-верификации. В уже существующем `iam_email_identity` источник истины — `verified_at IS NOT NULL` для действующего адреса; **не хранить второй противоречивый BOOLEAN**. Если email отсутствует, `emailVerified=false`.
2. **Изменение адреса:** новый email **обязательно проверяется заново**; `pendingEmailVerified=false` до успешного challenge. Пока проверка не пройдена, старый подтверждённый email остаётся действующим и его `currentEmailVerified` не сбрасывается. Только атомарное принятие proof делает новый CURRENT и verified; старый становится HISTORICAL. Указание идентичного нормализованного email — no-op, не изменение.
3. **Email proof ≠ аутентификация.** Проверка почты не выдаёт `VerifiedActor`, OIDC session, membership, tenant role, `CRM_PII_READ`, OWNER или PLATFORM_ADMIN; не восстанавливает SUSPENDED/DELETED пользователя. Email-dependent recovery, activation of email invitations и buyer order claim требуют **текущего** подтверждённого email и своей предметной проверки.
4. **Глобальный ключевой контур:** email, display name и phone принадлежат глобальному IAM. **Запрещено шифровать профиль tenant DEK**. Применять AES-256-GCM, независимый от него глобальный IAM encryption key и доменно-разделённый per-field AAD (userId, поле, версия); HMAC-SHA-256 blind index для equality email/phone. Секреты вне исходников/логов; неправильная generation/secret → fail closed.
5. **Не ломать существующий checkout:** `crm.sales_order.pending_email_identity_id` связывает исторический заказ с конкретным email identity. Нельзя при email change просто переписать `email_envelope`/HMAC у старой identity — сохранять immutable old identity. Перед cutover `findOrProvision`, verify и buyer-order claim обязаны исключать переназначение старых заказов.
6. **Текущая защищённость (проверено по коду `base_dev`):** `EmailIdentityCrypto`/ `EmailIdentityService` уже обеспечивают encrypted email, HMAC lookup, verification token и durable outbox (отправка провайдером пока HOLD). `iam_user_account.display_name`, `email_normalized`, `phone_e164` не зашифрованы на уровне приложения; email-change service отсутствует. **Не выдавать существующее CRM PII/KMS за защиту всех IAM-полей.**

### 25.2 Сервисный контракт, без нового framework

| Сценарий | Вход и предварительные условия | Правило результата |
|---|---|---|
| IAM-PII-01 Первичная регистрация | Новый user / trusted signup; email нормализуется текущим IAM codec | Encrypted PENDING identity, `verified_at=NULL`, `emailVerified=false` |
| IAM-PII-02 Подтверждение | Высокоэнтропийный one-time token, purpose и конкретная email identity | Проверка TTL/one-use (база: 15 минут), `verified_at`, единичное audit событие |
| IAM-PII-03 Смена почты | Текущий `VerifiedActor`, новый email и будущая step-up policy | Новый PENDING, старый CURRENT не теряется до proof; после успешного proof одно атомарное переключение |
| IAM-PII-04 Отмена / повтор / конфликт | Текущий пользователь; активный request | Повторы идемпотентны, истёкшие токены и чужие email не работают; ответ без account enumeration |
| IAM-PII-05 Профиль | Текущий `VerifiedActor`; имя/телефон и `rowVersion` | Профиль AES-GCM в отдельной `iam_pii` области, собственные PII только по self-access, нет plaintext-DTO для посторонних |
| IAM-PII-06 Исторические заказы | Checkout до и после смены email | Старые `email_identity_id`/order IDs неизменны; чужая перепривязка невозможна |

### 25.3 Данные и миграции

- `iam_user_account`: `userId`, статусы, `rowVersion` оставить типизированными; `external_subject` временно остаётся equality lookup OIDC под least-privilege DB (отдельный зафиксированный риск, не утверждать тотальное шифрование).
- `iam_pii.user_profile_secret`: целевые encrypted `display_name` и `phone` с keyed `phone_lookup_hmac`. Email **не дублировать** — использовать `iam_email_identity`.
- Существующий `iam_email_identity` требует минимальной версионируемой модели **PENDING/CURRENT/HISTORICAL**; у пользователя максимум один CURRENT и один PENDING, конкуренция подтверждений защищается индексами/транзакциями. Отказаться от прежнего `UNIQUE(user_id)` только с миграцией на partial uniqueness и изменением запросов. Historical identity нельзя считать разрешением login/recovery.
- Существующие `iam_email_verification_challenge` и `iam_email_delivery_outbox` **переиспользовать**; challenge привязать к purpose/target email, исключить proof из другого процесса; не плодить новый mail subsystem.
- Миграцию делать только новыми Liquibase changesets: additive schema → backfill из legacy → проверка на **заполненной** PostgreSQL с order FKs → переключение чтений/записей → удаление plaintext. Старые значения без проверяемого evidence **не превращать в verified=true** автоматически. Требуется безопасный план rollback/cutover и key recovery.

### 25.4 Обязательные критерии приёмки

**Не считать R2.5 завершённой**, пока H2 + PostgreSQL не доказали: регистрация `emailVerified=false`, первый proof → true, смена A→B с неизменным CURRENT до proof, cross-purpose и replay DENY, два одновременных владельца одного email → единственный победитель, invalid/suspended account DENY, integrity/AAD failure для ciphertext, отсутствие утечек через DTO/logs, сохранение исторических заказов, заполненная PG миграция/восстановление и fail-closed при недоступном глобальном IAM ключе.

**Граница:** всё выше — требования к следующей сервисной разработке в `base_dev`. Не писать контроллеры, SMTP-отправку, Redis, second identity service или universal privacy engine. Даже после сервисного GREEN остаются независимое security-review, реальный issuer/JWKS/OIDC/BFF, provider delivery, least-privilege, секреты/ротация, проверка backup/restore и production approval.

### 25.5 Результат IAM-PII-R2.5A — только внутренние сервисы

**Реализовано в `base_dev` (кандидат до merge):**
- `EmailIdentityService.registerPendingEmail(rawEmail)`: внутренний signup с прежним глобальным email dedup; новая identity имеет `verified_at=NULL`, шифруется AES-GCM и ищется по HMAC. Не раскрывает существование чужого пользователя. Для ACTIVE-аккаунтов этот неаутентифицированный путь не создаёт новый proof.
- `requestInitialVerification(VerifiedActor,email)`: первая почта активного OIDC-linked пользователя, проверка чужих и legacy адресов; не позволяет заменить уже привязанный email.
- `myVerificationStatus(VerifiedActor)`: self-only `emailVerified` из `iam_email_identity.verified_at`; отдельного BOOLEAN нет.
- `verifyRegistration(challengeId,token)`: одноразовое подтверждение только с purpose `REGISTRATION`; прежний checkout proof принимает только `CHECKOUT`. Email proof не выдаёт OIDC-session, tenant-роль или buyer-order claim.
- Liquibase `0044–0045`: purpose с DEFAULT CHECKOUT для прежних записей; события успешного proof и PostgreSQL immutability trigger. Существующие email identity IDs и order FK остаются без изменения.
- TTL challenge 15 минут, cooldown повторного registration challenge 60 секунд; это не заменяет HTTP anti-abuse и provider limits.

**Тесты:** `IamInitialEmailRegistrationQualificationTest` проверяет false до proof, encrypted envelope, single-use, purpose isolation, неактивные аккаунты, OIDC self-access, запрет смены email через initial method, конкурентные signup и proof, immutable event в PostgreSQL. Закреплять точный commit/CI при gate.

**Последующие этапы:** R2.5B реализован внутренними сервисами, квалификация и схема приведены в §25.6. R2.5C реализует encrypted CRUD и сервис отключённой по умолчанию миграции, но полный populated-PG production cutover ещё HOLD (§25.7). Real SMTP/email delivery, OIDC/BFF, key recovery и independent security review — HOLD.

### 25.6 Реализация R2.5B — смена почты с новой проверкой и сохранением заказов

**Изменения в `base_dev`, без HTTP:**
- `EmailIdentityService.requestEmailChange(VerifiedActor,newEmail)` создаёт отдельный CHANGE_EMAIL PENDING; старый verified CURRENT остаётся действующим. Повтор идентичного email — no-op; смена на чужой адрес или занятую активную identity — DENY.
- `confirmEmailChange(VerifiedActor,challengeId,token)` проверяет адресата, challenge purpose, expiry, hash и статус аккаунта. В **одной транзакции** прежний CURRENT становится HISTORICAL, новый PENDING становится CURRENT с `verified_at`; токен consumed и append-only audit. Отмена/повтор/неверный токен не меняет CURRENT.
- `cancelEmailChange(VerifiedActor)` отменяет только текущий CHANGE_EMAIL PENDING, не снимая подтверждения со старого адреса. Старые токены не могут активировать HISTORICAL identity.
- Новые Liquibase `0046–0048`: `lifecycle_state` (`PENDING`/`CURRENT`/`HISTORICAL`), `pending_reason`, отдельный `active_lookup_hmac`; уникальные nullable `current_owner_id`/`pending_owner_id` и active lookup. Исторические `lookup_hmac` и `email_envelope` сохраняются неизменными. **Существующие `crm.sales_order.pending_email_identity_id` не перезаписываются.**
- `AutoOrderService.verifyEmail/buyerOrders` учитывает только CURRENT verified email при подтверждении buyer claim. `findOrProvision` использует active lookup и не присваивает старый аккаунт владельцу заново зарегистрированного адреса.
- Внутренние тесты: нормальная смена, отмена, replay/cross-purpose, cross-account, повторное использование исторического адреса, параллельные подтверждения и реальный SALES order linkage. Реальный почтовый провайдер, BFF и rate limits на внешней границе пока HOLD.

### 25.7 Реализация R2.5C — AES-GCM профиля и staged plaintext removal

**Изменения в `base_dev`:**
- `GlobalUserProfileCrypto` использует собственные **глобальные IAM** ключи `RM_IAM_PROFILE_ENCRYPTION_KEY_BASE64` и `RM_IAM_PHONE_LOOKUP_KEY_BASE64`, не tenant DEK и не email lookup key. Для каждого поля AEAD AAD включает `userId` и имя поля; неправильная подпись, ключ и контекст отвергаются без plaintext fallback.
- `GlobalUserProfileService.myProfile/saveOwnProfile` возвращает/меняет только собственные имя и телефон по `VerifiedActor`, сверяя ACTIVE account, ограничение E.164 и `rowVersion`; возвращение plaintext разрешено только self. Сохраняет ciphertext/phone HMAC в `iam_pii.user_profile_secret` и audit без PII.
- `UserAccountEntity` больше не отображает legacy `display_name`, `phone_e164`, `email_normalized` для JPA-чтения/записи. Новый checkout не создаёт plaintext placeholder имени. Шифрование телефонов и имён нельзя обходить прямой записью JPA.
- Liquibase `0049–0051` добавляет отдельную IAM PII-таблицу и append-only audit; legacy `display_name` становится nullable. Старые колонки **пока физически существуют** ради безопасной offline migration.
- `LegacyIamPiiMigrationService.migrateUser/migrateBatch`: явный opt-in (`RM_IAM_PII_MIGRATION_ENABLED`, по умолчанию `false`), предназначен только для остановленного legacy контура. В транзакции зашифровывает имя/телефон, нормализует/шифрует legacy email при отсутствии identity, **не считает его подтверждённым**, проверяет конфликты и лишь затем очищает три plaintext-поля. При конфликте либо потере ключа — полный rollback.
- **Не закрыто:** автоматическая миграция в работающем сервисе, заполненная production-копия PostgreSQL с реальными коллизиями, завершение backup/restore, удаление legacy колонок/DB-пользовательских прав, доказательство отсутствия альтернативных SQL writers, управление жизненным циклом/ротацией глобальных IAM ключей. Сервисная миграция и зелёный synthetic CI не заменяют cutover-gate.

**Условия допуска:** отдельное security-review PR #9, прогон migration и восстановления на обезличенной копии заполненной БД, проверка возможных конфликтов почты, обязательная сверка исторических заказов, внешний anti-abuse/SMTP/OIDC и DB least-privilege. Текущая стадия — разработка сервисов и квалификация; `main` не изменять до согласования.
