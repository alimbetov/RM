## Partitioning decision
Do not migrate core task tables while release is HOLD without measured evidence. Current C3 ordered state index already yields sub-ms EXPLAIN on observed variant; partitioning cannot remove IAM round trips or shared CPU/IO. Current TASK tables have tenant-scoped PKs, FK task_event→task_item, create request uniqueness, per-task/version uniqueness and tenant command-request idempotency. PG unique keys on partitioned parents must include every partition key. RANGE(due_at) on mutable tasks would move rows on reschedule and break existing uniqueness shapes; RANGE(occurred_at) on task_event would break global per-tenant/task/version and command-request uniqueness unless redesign with separate uniqueness registry. No time partition as default.

Candidate if EXPLAIN/BUFFERS and concurrency prove tenant scan/IO bottleneck: HASH(tenant_id) on task_item and task_event (same modulus, e.g. 8 or 16 candidate, not preapproved), all existing unique keys/FKs include tenant where applicable; inspect every constraint/reference/trigger and actual migration first. Local parent-declared indexes propagated to children; pruning by exact tenant; cannot reduce single hot tenant below one partition. Existing idx_task_queue(tenant_id,status,due_at,id), idx_task_assignee and event order index retained until measured. F2 candidate nonpartitioned partial terminal-evidence index (tenant_id,task_id,new_version), covering only exact terminal predicate and tested include columns if plans demonstrate event scan; no unmeasured write amplification.
