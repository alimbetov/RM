## 3. Cross-method correctness & security findings

| Finding | Severity | Source-level fact | Smallest proposed resolution + test |
|---|---|---|---|
| **SA2-01** | **P0** | Checkout snapshots title and price, **not SKU**. Confirmation and reservation both JOIN current `store_offer.catalog_item_id`. | Add immutable SKU reference to line at creation, use consistently in both commands; test mutate/unpublish offer after checkout → same original SKU/price reserved |
| **SA2-02** | **P0** | Checkout verifies only PUBLISHED offer and currency, not a nonnull mapped PRODUCT catalog item/state. | Require eligible same-tenant PRODUCT SKU at checkout; reject unmapped/archived/foreign item without any order/email/outbox side effect |
| **SA2-03** | **P0** | `confirm` does not consult `org_location.status/type`; stock FK proves tenant binding only. | Typed ORG ACTIVE WAREHOUSE read-lock + status guard; race with deactivation after separate ORG lifecycle acceptance |
| **SA2-04** | **P0 functional** | `InventoryTenantSettingsService.auto_reserve_on_confirm` is writable; SC-01 never reads it and always reserves. | R1 always reserve; remove/freeze advertised toggle rather than add alternate state machine |
| **SA2-05** | P1 | SC-02 always requests INVENTORY_RELEASE even when PLACED has no reservation; may deny permitted commercial cancellation. | Subject decision: PLACED cancellation needs SALES_ORDER_CANCEL only if no reserves; CONFIRMED cancellation keeps both grants. Test least-privilege actors with/without stock rights |
| **SA2-06** | P1 | AO-03 runs unbounded `SELECT` for all buyer orders, and SQ-01 lacks seller detail/history. | Typed bounded buyer paging and seller detail/events; test 100+ orders, foreign ID, staff A/B |
| **SA2-07** | P1 | Checkout uses independent unlocked `SELECT` for each offer; concurrent offer title/price edits can produce a basket with inconsistent publication revision. | Lock each offer in deterministic offer-ID order and freeze all line values in transaction; preserve checkout stripe→IAM email lock order; test simultaneous price mutation/unpublish |
| **SA2-08** | P1 | Validation bounds each input quantity ≤1000 and input line count ≤100, but merging duplicate offer IDs can produce aggregate qty >1000; `Math.addExact` may throw `ArithmeticException` instead of controlled validation. | Choose max qty per merged SKU (recommend ≤1000) and reject surplus as input error; test duplicate lines, overflow, 100 identical offers |
| **SA2-09** | P1 | `verifyEmail` intentionally links ALL `sales_order` rows with matching verified global identity across tenant sellers; return value is internal raw user UUID. | Preserve global buyer identity semantics; add test two tenants + proof + status/history, deny wrong purpose and no session issuance. Keep proof method internal trusted transport |
| **SA2-10** | P1 | `sales_order_status_event` stores status/time only; seller cannot view immutable timeline, no actor or reason. | Existing event table + additive optional actor/reason; read-only scoped history. No duplicate audit engine |
| **SA2-11** | P1 | Checkout checks published storefront slug but no explicit `iam_workspace.status='ACTIVE'` join and no concurrency fence for storefront pause/tenant suspend. | Define admission to active tenant, transaction-safe pause/checkout ordering. Do not invent status conditions until verified with populated tenant fixtures |
| **SA2-12** | P1 | The two SELECTs for SQL COUNT and page are separate statements under default isolation; stable ORDER BY does not guarantee a simultaneous snapshot across concurrent status updates. | Document offset semantics, use bounded paging; exact-snapshot or cursor only when product needs it. Do not falsely claim SQL injection (all filters bound) |

**Correction to generic audit wording:** `cancel(PLACED)` is **implemented** but its stock permission may be unnecessarily restrictive; `verifyEmail` has cross-tenant updates by global identity **by design**, not automatically a tenant-isolation bug. Raw checkout/verify methods must not be exposed as HTTP, but their public Java visibility alone is not evidence that they are externally reachable.

## 5. Method-level TЗ delta before PASS 03

1. **SALE-R1.A P0:** Source-of-truth SKU: `sales_order_line.catalog_item_id_snapshot` chosen at checkout. Both `SalesInventoryCommandService.lines` and `InventoryReservationService.reserve` must use it. Scope schema/legacy backfill and populated migration in PASS 03, not now.
2. **SALE-R1.A checkout:** Snapshot title, price, currency and SKU in the same transaction using safely locked offer rows, validate published tenant SKU and aggregate qty; do not let buyer input price/status/tenant.
3. **SALE-R1.B read:** `AuthenticatedSalesQueries.get/history` and `AuthenticatedBuyerOrders.mine(page,size)/ownDetail`; enforce PII-free projections and exact tenant/buyer WHERE.
4. **SALE-R1.C:** ORG typed location guard, INV always-reserve semantics, least-privilege PLACED cancel decision after product approval.
5. **SALE-R1.D:** Explicit qualified CATALOG → STOREFRONT offer management, not automatic publish. Future `StorefrontManagementService` only if proven required.
6. Keep `SALES_ORDER_CONFIRM`+`INVENTORY_RESERVE`, `SALES_ORDER_FULFILL`+`INVENTORY_FULFILL`, `OrderInventoryPort` transaction-bound decisions and CAS/idempotency intact. No new generic workflow engine, microservice, outbox or controllers.
